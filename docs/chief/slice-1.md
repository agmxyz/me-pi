## Scope

In: one chief per repo; tasks with landings `none`, `in-place`, `branch`; headless one-shot coordinator runs; attach; cancel; drop.

Out (agreed cuts): PR delivery, standing approvals, the `after` field, spend tracking, a worktree setup command, automatic worktree removal, exit confirmation, any hard timeout. "Guard in coordinators" and "the guard refactor" were cuts until #197 (the user's decision of 2026-11-27): see [Guard](#guard). `skills/batch-chief/` stays in use for PR work.

## Parts

| Part | Path | Owns |
|---|---|---|
| Script | `skills/chief/chief.ts` | the event log, every state change, launch, the run wrapper, reconcile |
| Extension | `extensions/chief.ts` (private setup, not `@agmxyz/pi-workers`) | `/chief`, user-only commands, wake on run end, the edit block, the other-session notice |
| Skill | `skills/chief/SKILL.md` | judgment: writing briefs, choosing a landing, reviewing, when to ask the user |
| State | `<repo>.worktrees/.chief/` | `events.jsonl`, `lock`, `tasks/<id>/{brief.md,contract.md,runs/<n>/{report.md,stream.jsonl,stderr.log,exit}}`, `notes/` (the chief's memory) |

State files are created private (0600): run streams hold every command a coordinator ran.

## The log and its one lock

State is the replay of `events.jsonl`. Every writer (chief commands, run wrappers, attach, reconcile) takes the single repo lock, replays, checks its guard, appends, and releases. No command checks and appends in separate steps. Replay is idempotent per run id, so evidence consumed twice changes nothing.

## Chief lease

```
FREE --/chief--> HELD(session, generation) --controlled exit--> FREE
HELD --holder gone, or user confirms takeover of a live holder--> HELD(generation+1)
```
- `/chief` is the only way in, and only in an interactive session.
- The extension passes its session id and generation to every script call that changes or records anything (`claim` is given its generation, and `state` only reads); the script refuses a caller whose generation is not current. This fences a displaced chief's commands, its wakes, and its shutdown (an old session ending must not release a successor's lease).
- A session that is killed releases nothing, so a lease can be left held by a dead session; the next `/chief` finds the holder gone and reclaims. (Written as "Pi has no hook before exit or `/reload`"; it has `session_shutdown`, which #190 uses for the controlled exit.)
- `/chief` is refused while a `batch-chief` run is unfinished. Batch preflight is refused while the chief log has any task with a live or unexplained run, whether or not a lease is held. This needs one edit to `skills/batch-chief/batch.ts`.

As built (#189), in the script:
- The lease is in the log: `lease-claimed` (session, generation, the session's process by pid and start time) and `lease-released`. A claim's generation is one above the last claim's, released or not, so no generation is given twice. Lease events name no task and change none: a claim or takeover starts, stops and records nothing of a run.
- A caller says who it is before the command: `chief.ts --session <id> --generation <n> <command>`. Every command but `claim` and, since #190, `state` is refused without them, `status` and `reconcile` included: they record what became of a run, and a displaced session's wake is dropped by that refusal. The check is made under the repo lock every time the log is read, and a launch starts its wrapper, and a `cancel` sends its signals, under a lock that made it: a session displaced partway through a command starts and signals nothing more. A process of the run that `cancel` finds outside the wrapper's group is in the log before it is signalled. A launch displaced after its reservation writes no contract and its run is recorded as one that never started (`launch-failed`); a `cancel` displaced after it was recorded leaves the task `STOPPING` for the new chief's `status` or `cancel`.
- `chief.ts --session <id> claim [--pid <pid>]` claims. `--pid` is the process that is the session (the script's own when not given, which is gone when the script ends; the extension passes Pi's). It is refused while the holder's process runs, by pid and start time, whichever session asks, and while the process table cannot be read; it succeeds when the lease is free or the holder is gone.
- `claim --takeover <generation>` displaces a holder whose process is alive. The script cannot tell whether a live session responds: that is the user's judgment, so it is taken only from a caller that says it is the user, like the user's `answer`. It names the generation of the holder the user was shown, and is refused when that is no longer the lease held. The event records `takeover` when the holder was not known to be gone.
- `release` is the holder's controlled exit and frees the lease. From a displaced session it is refused like any other command, so an old session ending releases nothing.
- A run's wrapper is not fenced: its run goes on, and is recorded, whoever is chief.
- The mutual refusal with `batch-chief`, as built (#193):
  - `claim` is refused, for a takeover too and before any chief state is created, while the repo's current `batch-chief` run is unfinished. What unfinished means is `batch.ts`'s to say, in one function both sides use (`unfinishedRun`): a row that is not terminal, a live check still owed, or a log of another helper version, which is never replayed and so cannot be told to be finished. A run whose rows are all terminal is finished whether or not its `cleanup` cleared the pointer.
  - An event that reserves a run (`launch`, `round`, `answer`) is refused the same way, so a batch started while a session was already chief (by a helper older than this, or between two looks) is joined by no run of the chief's. `status`, `reconcile`, `accept` and the user's commands are not refused: they start nothing.
  - `batch.ts preflight` is refused while a chief task is `LAUNCHING`, `RUNNING` or `STOPPING`, which an unexplained run always is. It asks the chief's own script (`node chief.ts state`, which needs no lease, takes no lock and reconciles nothing), so the answer is the same with a lease held, free, or left by a dead session, and a run whose processes are gone but whose end nobody has recorded still refuses: `/chief`, then `status`, records it. Chief state that is there and cannot be read (the script missing beside a copied skill, a log replay refuses) is a refusal too, never taken as no live run. With no chief log the script is not asked.
  - The two sides share no lock, so each looks twice, the second time after it has published what the other reads. `preflight` asks `state` before it does anything and again once its run is the current one; a chief run found then puts the pointer back as it was and refuses, leaving the new run's directory with only its preflight. A reservation looks for a batch under the repo lock and again once it is in the log; a batch found then leaves the run `FAILED(launch)`, with no worktree, contract or wrapper. Of a preflight and a reservation made at the same moment at least one sees the other; both may, and then neither starts.
  - A batch may start under a chief that holds the lease with no run live: the criterion is a run. That session keeps its lease, `state` says so (`batch`), `/chief` in it warns that no run is started, and a lease left by a failed `release` is not taken up again beside a batch.
  - Whether a batch run is unfinished may not be readable (a log its helper does not replay as JSON, a pointer to a run that is gone): that refuses a claim and a reservation like an unfinished run, and `state` says so in `batch` and still shows the lease and the tasks.
  - Not covered: the look-twice argument is for one preflight and one reservation. `batch.ts` has no lock of its own, so a third writer of its pointer at that moment (a `cleanup` of the run before, a second preflight) is outside it; `cleanup` and a refused preflight now touch the pointer only while it names their own run, which is checked and then written, not in one step. Between a preflight's publication and its second look its run is the current one for any `batch.ts` command. A batch started by a `batch.ts` older than this change asks nothing of the chief, and is met only by the chief's own refusals. An `ATTACHED` task does not refuse a preflight: the criterion is a live or unexplained run. A batch run in another repo, or under a main checkout the script does not find, is not seen. A coordinator's run that was `FAILED(launch)` by the second look counts toward the task's retry cap.
- Not covered: nothing stops a session from passing another's session and generation. A way to read the log without holding the lease came with #190 (`state`, below), and so did what `/reload` does to the lease.

## Task lifecycle

```
QUEUED --launch--> LAUNCHING --wrapper confirms spawn--> RUNNING(run n)
LAUNCHING --spawn never confirmed--> FAILED(launch)
RUNNING --run ended--> REPORTED | ASKED(chief) | FAILED(reason)
RUNNING --cancel--> STOPPING --all processes gone--> FAILED(cancelled)
ASKED(chief) --answer (a line of the brief, once per task)--> LAUNCHING
ASKED(chief) --escalate--> ASKED(user) --answer (user)--> LAUNCHING
REPORTED | FAILED --round--> LAUNCHING
ASKED | REPORTED | FAILED --attach [a run of the task started Pi]--> ATTACHED --detach--> the prior state, or ASKED(user) when the checkout is not as recorded
REPORTED --accept--> ACCEPTED
REPORTED | FAILED | ASKED --a recheck finds the checkout not as recorded--> ASKED(user)
RUNNING | LAUNCHING | STOPPING --run ended with the checkout on another branch--> ASKED(user)
ASKED | REPORTED | FAILED --cleanup (user) removed the task's worktree--> ASKED(user)
QUEUED | ASKED | REPORTED | FAILED --drop (user)--> DROPPED
```
- `FAILED` reasons: `launch`, `crash`, `lost`, `provider`, `no_report`, `cancelled`.
- No drop, cleanup or round while `LAUNCHING`, `RUNNING`, `STOPPING` or `ATTACHED`.
- No attach on a task none of whose runs started Pi (a `QUEUED` task, a first launch that failed): it has no session (#193; the lifecycle above listed `QUEUED` until then).
- A run whose owner cannot be established (wrapper gone, process state unclear) blocks round, attach, cleanup and signalling on that task until reconcile explains it.
- After two consecutive `FAILED` runs, a further round needs the user.
- At most four tasks in `LAUNCHING` or `RUNNING`; one per checkout.
- Every run has a deadline (default 90 minutes; 45, a guess, until #193). Passing it marks the task `OVERDUE` and wakes the chief; nothing is stopped.
- Where 90 comes from: the 13 headless build runs of this branch took 12 to 80 minutes; 3 of the 13 ran over 45 minutes, 2 over 60, none over 90. The acceptance run (#194) is still to confirm it. The limit of four and the retry cap of two are as they were, and still unmeasured.

## A run

**Launch**, in this order, each step logged before the next:
1. Under the lock: check the brief has goal, "done when", landing and scope, each as a line that starts with `Goal:`, `Done when:`, `Landing:` or `Scope:` (any case) and says something; check capacity and that the checkout is free; record the reservation (`LAUNCHING`).
2. For `branch`: create the worktree and branch. For `in-place`: require a clean tree and record branch and commit.
3. Write the contract from the brief and recorded approvals.
4. Start the wrapper detached, in its own process group, and record its identity.
5. The wrapper takes the task's run lock, records its own identity (refusing to go on unless the task is still `LAUNCHING` that run), starts `pi -p --mode json --session-id <session> --model <chief's model>` with `ME_PI_UNATTENDED=1`, with `ME_PI_GUARD=off` when the run was reserved with guard off and without that variable otherwise ([Guard](#guard)), and with the contract as the prompt, and records both process identities (pid and start time). The task is now `RUNNING`.

**Session per run (proposed).** The first run of a task uses session `<task>-1`. A round after `REPORTED` or `ASKED` reuses the last session. A round after `FAILED` with reason `crash`, `lost` or `cancelled` starts session `<task>-<n>`, with the brief and the previous report in its prompt: a session killed mid-tool cannot be resumed ([spike set 2](spikes.md)).

As built (#186), a round after `FAILED(launch)` starts a new session too: nothing says whether Pi ran. The `launch`, `round` or `answer` event that reserves a run records its session. A round uses the model and checkout its task was launched with. The contract of a run after the first has a section saying whether its session goes on, and holding what the round brings: the chief's message or the answer, and in a new session the last report an earlier run left. A prompt is one argument of Pi's command line, so a carried report longer than 20,000 characters is cut, with the path of the whole, and a longer message or answer is refused.

**Questions and rounds.**
- `answer <task> --line <text>` is the chief's answer. The text must be a whole line of the task's brief, and the log takes one such answer per task. Anything else is `escalate <task>`, which gives `ASKED(user)`.
- `answer <task> --words <text>` is the user's answer, the only event that leaves `ASKED(user)`. The script takes it only from a caller that says it is the user; run as a process the script never is, and the extension is that caller when the user types `/chief answer <task> <words>` (#191).
- `round <task> [--message <file>]` starts a run on a `REPORTED` or `FAILED` task. A `REPORTED` task needs the message (a fix, a review's findings); a `FAILED` task without one is retried, and the retry is brought what the failed run was brought.
- A task that asked, with no run `REPORTED` since, has an open question: a round on it takes no message, so a failed run opens no second answer. The retry brings the answer already given.
- After two `FAILED` runs with no `REPORTED` or `ASKED` run between them, whatever the failure's reason and whatever the round was for, `round` is refused until a `cap-lifted` event, which is the user's to record (`/chief lift <task>`, #191) and starts the count again. The count is the task's: a second task added with the same brief starts its own, which the script does not prevent.
- Each run writes its report to `runs/<n>/report.md`; the contract of run `n` names that path.

**Result.** Read both, never one:
- Process exit status: 143 or 137 means signalled; non-zero with an empty stream means the invocation failed.
- The stream: a completed run ends with `agent_settled`, not aborted; the last assistant message's stop reason tells success (`stop`) from provider error or abort, and a failed reply is `FAILED(provider)` whether or not the stream goes on to settle. Pi exits 0 on a failed reply in JSON mode.
- Then the run's own `report.md`: missing after a completed run is `FAILED(no_report)`, whatever an earlier run left; its first line is exactly `DONE` or `BLOCKED`, and any other first line is `FAILED(no_report)` too.

A signalled Pi and a failed invocation are `FAILED(crash)`; Pi's error output stays in the run's `stderr.log`, and its end is kept in the `run-ended` event with the reason.

The wrapper writes `exit` by write-then-rename, then appends `run-ended`. If the wrapper dies between the two, reconcile finds the file and appends the event once.

**Reconcile** runs under the repo lock in `status`, `reconcile` and every command on an existing task, for each `LAUNCHING` or `RUNNING` task. The reservation names the launching process; a process counts as the run's only while its pid has the recorded start time. In order:
- exit evidence without its event becomes `run-ended`;
- the wrapper (or, before one is recorded, the launch) is alive: nothing changes;
- the wrapper is gone and Pi, or any process of the wrapper's process group, is alive: the run is unexplained; `status` names it under the task, nothing is recorded, and commands on the task are refused;
- nothing is left, by the process table and by asking the system whether the wrapper's process group has a member: `FAILED(lost)`, or `FAILED(launch)` when Pi's start was never confirmed;
- a start time that was not recorded, or a process table that cannot be read: unexplained.

**Stop.** `cancel` signals the whole process group with SIGTERM, waits, then SIGKILL, and leaves `STOPPING` only when no process of the group is left. SIGKILL of Pi alone left its command's children running (spike set 2).

As built (#187): Pi starts each command of a coordinator in a process group of that command's own, which a signal to the wrapper's group does not reach. So the run's processes are the wrapper's process group, every child of a process of the run, and every member of a process group one of them is in. `cancel` records the ones outside the wrapper's group with their start times (once their parents are gone nothing else ties them to the run), signals the group and each of them, and waits five seconds after each signal. A process seen later, while the task is `STOPPING`, is recorded the same way by whoever sees it. A process that left both its parent and its group before anything looked (a daemon) is not found, and neither is a command's process once the wrapper and Pi are both gone and no `cancel` had recorded it. A process is checked by pid and start time when it is looked up, not when it is signalled: a pid given out again in between would be signalled. A run that ends of its own accord while its `cancel` is being recorded is still `FAILED(cancelled)`; its report stays in its run directory. A task still `STOPPING` after SIGKILL is an error; `status` names what is left, and `cancel` on a `STOPPING` task signals it again. `status` and `reconcile` record `FAILED(cancelled)` once nothing is left, so a `cancel` that was itself killed loses nothing.

**Limit and deadline, as built (#187).** The event that reserves a run (`launch`, `round`, `answer`) is refused, at the command and at replay, while four other tasks are `LAUNCHING` or `RUNNING`, or while another task's run in the same checkout is `LAUNCHING`, `RUNNING` or `STOPPING`. A `STOPPING` task is not one of the four. `add <task> … --deadline <minutes>` sets a task's deadline; a run is past it that many minutes after it was reserved. `OVERDUE` is not a recorded state: `status` shows it beside `LAUNCHING` or `RUNNING`, from the clock.

**Background delegate jobs** are refused in print and JSON modes. This is a change to `packages/pi-workers/extensions/delegate.ts` keyed on the mode, not on `ME_PI_UNATTENDED` (which `batch-chief` coordinators also set), with a line in that package's `CHANGELOG.md`. Foreground delegate works in print mode (spike set 2).

## Guard

Added by #197, after the build. Until then this page said coordinators ran without guard and that nothing enforced the contract's list of commands. The wrapper started plain `pi` without disabling extensions, so guard loaded and blocked in unattended sessions where Pi's settings included it. A user package filter could exclude `guard.ts`, however, so not all pre-#197 coordinators were necessarily guarded. The contract separately carried a stricter copy of guard's rule. Now:

- **Guard is the only owner of the rule.** What is blocked is `packages/pi-workers/extensions/guard.ts`'s to say. The script and the contract name no command.
- **A coordinator follows the guard state of the chief session that starts its run.** With guard on in the chief's session, which is the default, the run has guard: a command guard blocks does not run, guard says so with its reason where the command's output would be, and the contract tells the coordinator to report it `BLOCKED` with the command and that reason, not to route around it. With guard off in the chief's session (the user typed `/guard off` there), the runs started from then on are unguarded, until `/guard on`.
- **A live run keeps the state it started with.** The state is fixed when the run is reserved; toggling guard in the chief's session afterwards changes the next run, not this one.
- **Approvals do not reach guard.** An approval is copied into the contract and read by the coordinator; guard does not read it. So a destructive command the user approved is still blocked in a guarded run: it needs a run started with guard off, which is the user typing `/guard off` in the chief's session before the round, and `/guard on` after it if they want it back. Approvals reaching guard is not part of slice 1.

As built (#197):
- **Guard can be started off.** `ME_PI_GUARD=off`, set by whoever launches a session, starts guard off in it: it blocks and asks nothing, with or without a UI, unattended or not. Only that value does; any other, or none, starts guard on, so every session not started with the variable is as before. `/guard on` turns it on. `/guard off` typed in an unattended session is still refused: one started off stays off, and one turned on there cannot be turned off again. A delegate worker always starts with guard on, whatever its coordinator was started with: it inherits the variable, and guard ignores it in a worker.
- **Where the state comes from.** The extension asks guard, in the chief's own session, over Pi's event bus (`me-pi:guard-query`), at `/chief`, and guard says its state after every `/guard on` or `/guard off` (`me-pi:guard-state`). The extension records it with `chief.ts … guard on|off`, which the script takes only from that caller (`userOnly`): run as a process, which is all a model's `bash` reaches, it is refused, so a chief cannot turn guard off for its coordinators by calling the script. The extension holds no rule of guard's and keeps no state of it.
- **Where it is kept.** On the lease: a `lease-guard` event, by the session and generation that hold it, recorded when the state differs from the one the lease has. A lease starts with guard on, so a claim or a takeover by another session starts guarded until that session's own state is recorded, which `/chief` does before the session can start a run. `state` shows `unguarded` in `lease` while it is off.
- **What a run records.** The event that reserves a run (`launch`, `round`, `answer`) takes the lease's state under the lock that records it, and says `guard: "off"` when the run starts unguarded; without it the run is guarded. No command takes the state as an option. At replay, a reservation that says `off` under a lease that does not is refused, and so is a value other than `off`.
- **What the wrapper does.** It starts Pi with `ME_PI_GUARD=off` for a run reserved so, and otherwise removes that variable from Pi's environment, so a wrapper that inherited it from its own launcher still starts a guarded run.
- **What is shown.** `launch`, `round` and `answer` answer `LAUNCHING run <n>, unguarded`, and `status` shows `run <n>, unguarded` on a task whose last run started, or starts, with guard off, live or over. The message `/chief` sends the session says which state it has and that a run starts with the state of then, and a `/guard` the user types reaches the session as a message that starts no turn.
- **The contract.** One rule in place of the list: guard may block a command and says so with its reason; an approval does not lift that; the coordinator does not run the command another way, and reports `BLOCKED` with the command and guard's reason, with any secret replaced by its variable name. `DESTRUCTIVE` and its test are gone. `git branch -D` is not blocked in a coordinator: guard asks about it only in delegate workers, and a coordinator may run it, as the main session may (the user's decision).
- Not covered: a chief session whose settings do not load guard (a package filter that excludes `extensions/guard.ts`) has no state to record, records none, and is told so; its runs start without `ME_PI_GUARD`, so a coordinator then has guard exactly when Pi's settings load it for the coordinator, which are the same user settings; the extension reads guard's state when `/chief` is typed and after each `/guard`, so a guard toggled by anything else than its own command is not seen; a `/guard` typed while the script cannot record it (the repo lock held for 15 seconds, a session displaced since) is shown as an error once, the lease keeps the state it had, and every look (5 seconds) tries again; while it is `/guard on` that is not recorded the session reserves no run, since the lease still says off: its `bash` is blocked (the model's only way to `launch`, `round` and `answer`), the user's `/chief answer` tries the recording again and is refused if that fails, and a wake waits, since the session could not read `status`; a `/guard off` that is not recorded leaves runs guarded and blocks nothing; each try runs in Pi's own process and waits for the repo lock like `claim` and `release`, up to 15 seconds; a guarded coordinator can start a Pi of its own without guard (`ME_PI_GUARD=off pi …`, as it could with `pi --no-extensions` before this), which guard does not ask about: the contract's rule forbids it, nothing enforces it, and the run's stream shows it; the state is the lease's, so after `/reload` or a new `/chief` it is recorded afresh from the session as it is then; guard is a pattern match on `bash`, not a sandbox, so an unguarded run is not the only way a destructive command runs (interpreter code, a non-recursive `rm`), and a guarded coordinator that ignores the contract's rule can route around a block, which its stream shows; the two runs of the acceptance criterion were shown with the fake `pi` loading the real guard handler, not with a real Pi.

## Checkout identity

A clean tree is not enough. The script records checkout path, branch and commit at launch, and the commit the chief reviewed. Before every round, after every detach, and before `accept` it rechecks them. A switched branch, a missing worktree or changes no run explains move the task to `ASKED(user)` with what was found; nothing is reset or restored.

`accept` per landing: `none` needs a clean tree; `in-place` needs a clean tree and a new commit on the recorded branch; `branch` needs a clean worktree and the branch ahead of its base. The accepted commit is recorded.

As built (#188), for `none` and `in-place`:
- The script reads a checkout with `git rev-parse --show-toplevel` and `git status` (told to take no lock), and `accept` on an `in-place` task also asks `git merge-base --is-ancestor`. It runs no git command that changes a checkout (since #192, two do: `git worktree add` at a `branch` launch and `git worktree remove` at the user's `cleanup`).
- `launch` records the checkout `as` found: branch, commit, and tree, which is empty when clean and otherwise a fingerprint of what `git status` lists and of what each listed file holds (a file over 8 MB by its size and write time). An `in-place` launch is refused unless the tree is clean and the checkout is on a branch. A `none` launch takes any tree.
- Every event that ends a run (`run-ended`, `launch-failed`, `stopped`) records the checkout as `found`: what the run left. The wrapper reads it as Pi exits and publishes it as `runs/<n>/checkout.json` before the exit status, so a wrapper killed after that loses nothing and a later reader does not take in changes made since. The end of a run that left no exit evidence (lost, never started, cancelled) is recorded with the checkout as it is then. This is the reviewed commit: the chief reviews a `REPORTED` run, and `accept` takes the checkout only as that task's run left it.
- A run that ends with the checkout on another branch than the task's moves the task to `ASKED(user)` at once, however it ended; what was found names how the run ended.
- The recheck runs under the repo lock before every run after the first (`round`, `answer`) and before `accept`. It finds a checkout that cannot be read (a removed worktree is one, and so is a directory that is no longer the top of a working tree), a branch other than the one recorded at launch, a commit or tree that is not what the task's own last run left (another task's run in the same checkout included), and a run whose end was recorded while the checkout could not be read. It records `checkout-changed` with what was found, the task becomes `ASKED(user)`, nothing is started or accepted, and the command is refused saying so. `status` shows what was found under the task.
- The user's `answer` leaves it, and records the checkout it was given for; the run it starts is told what was found. A checkout that changed again since the user was shown it is found, and recorded, again instead, and one that still cannot be read starts no run. So is one put back as the run left it: an answer is taken only for the checkout the user was last shown. The answer does not change the task's branch: a run that ends on another branch is found again. It is the user's, so it starts a run on a task at the retry cap without a `cap-lifted`; the count goes on from where it was.
- `accept` on a checkout that is as the run left it, with changes in the tree, is refused and the task stays `REPORTED`: a run explains those changes, and a round can have them committed or removed. For `in-place`, a commit that is the launch commit, or that does not have it behind it, is refused the same way.
- The `accept` event records the checkout accepted, and `status` shows the commit.

As built (#192), for `branch`:
- **Where.** `launch` gives a `branch` task the worktree `<repo>.worktrees/<task>` on a new branch named `<task>`, both made from the commit the checkout `launch` was run in is at (its base); that checkout's branch and tree do not matter, and it is only read. The launch is refused, with nothing touched, while that path or that branch exists, or while there is no commit yet.
- **Launch.** The reservation (`launch`) names the worktree as it will be made: on the task's branch, at the base, clean. Under the next lock the script runs `git worktree add -b <task> <path> <base>` in the main checkout and records `worktree-created`; then the contract and the wrapper, as for any landing, and Pi runs in the worktree. A `git worktree add` that fails leaves `FAILED(launch)`; a round on that task has no checkout to recheck and makes the worktree. A launch killed after git made the worktree and before `worktree-created` leaves one the round finds exactly as it makes it (that branch, the base, clean) and takes as made; one killed when git had made only the branch leaves a branch at the base with nothing at the path, which the round gives its worktree (`git worktree add <path> <task>`). Anything else at that path, and a branch of that name at another commit, is left alone and fails the launch.
- **Accept.** `branch` needs a clean worktree and the task's branch ahead of its base: a commit that is not the base and, asked of `git merge-base --is-ancestor`, has the base behind it. The recheck is the one every landing has, on the worktree: a worktree that is gone, on another branch, or not as the task's last run left it moves the task to `ASKED(user)`. Nothing is merged; the branch stays for a later local merge.
- **Cleanup.** `cleanup <task>` is the user's (`/chief cleanup <task>`), refused by `userOnly` from anyone else. It removes only a worktree a `branch` launch made, with `git worktree remove <path>` and never `--force`. The task's state is looked at before who asks: it is refused while `QUEUED`, `LAUNCHING`, `RUNNING`, `STOPPING` or `ATTACHED`, so under a live run and under an unexplained one, which is always one of these. It is also refused while another task's run is live in that worktree, while a process of the task's last run is left though the run is over (a command of the coordinator's that outlived Pi; found as `cancel` finds a run's processes, and refused too when the process table cannot be read), while any process holds the task's run lock (taken without waiting, and held over the removal), when the worktree cannot be read or is on another branch than the task's (commits made there may be on no branch that is kept), and when `git status` lists a change or an untracked file there or `git status --ignored` an ignored one (both told to list untracked files whatever the user's git configuration says); the refusal lists them. A removal git refuses is not tried again: it is a refusal while the worktree is still as it was looked at, and otherwise a failure (code 2) that records nothing, which the next recheck finds.
- **The branch is never deleted.** The script runs no `git branch` command; a worktree's removal leaves its branch, and the commits on it, in the repo.
- **After a cleanup.** The `cleanup` event is recorded once git removed the worktree. An `ACCEPTED` or `DROPPED` task stays as it is. Any other task has lost its checkout and becomes `ASKED(user)`, saying so. The user's `answer` leaves it only once a worktree is readable at that path again, which is theirs to put back (`git worktree add <path> <task>`); it is then shown to them first, like any checkout that changed since they were last shown it. A worktree put back so is the task's again, and a later `cleanup` removes it.
- A worktree removed by anything else (the user's own `git worktree remove`, an `rm`) is found by the recheck, before a round, an answer's run or `accept`: `ASKED(user)`, nothing made again.
- Not covered: a `branch` task's base is the commit of the checkout `launch` was run in, whatever is going on there, so one launched beside a live `in-place` run, or after one that is not accepted, takes that run's commits as its base, and they are then on the task's branch whether or not the `in-place` task is ever accepted; commits made in the worktree that no branch holds (made on a detached `HEAD` before it was put back on the task's branch) are no longer reachable from the worktree's `HEAD` log once it is removed; a process of an earlier run than the last, and one that left its parent and its group before anything looked, is not found (as for `cancel`); that an accepted `branch` commit has the base behind it is asked of git by the command and not checked again at replay, as for `in-place`; a launch killed between git making the worktree and `worktree-created`, on a task that is then dropped instead of retried, leaves a worktree `cleanup` does not know and the user removes with git; a worktree the user made themselves at the task's path, exactly as the launch makes it, or a branch of the task's name they made at the base, after the reservation and before the launch got there, is taken as the task's; a last run whose wrapper's start time was not recorded, with its pid now another process's, keeps `cleanup` refused as it keeps `cancel`, until that process ends; a worktree whose directory is gone while git still lists it is refused by `cleanup` as unreadable, and `git worktree prune` is the user's; `status` names a task's worktree as made whether or not it is still there; the worktree's path and the branch's name are the task's id and cannot be chosen, and the base is the commit of the checkout `launch` was run in, not a named ref; a worktree removed under an idle task is found at the next recheck, not by `status`; an ignored file written between the look and git's removal is lost (git itself refuses for a change or an untracked file); a `branch` task whose first launch found something else at its path on another branch is `ASKED(user)` and has no checkout an answer could be given for until the user makes that path the task's worktree, or drops it; a `QUEUED` task has no worktree, and a worktree no launch of the chief's made is never removed by `cleanup`; the removal runs under the repo lock, so a slow one holds other commands up to their 15 seconds; `cleanup` was tested with real git through the extension's handler and a fake Pi, not typed in a real session.
- Not covered (#188): a file `git status` does not list (an ignored one); a change made after the last look and before a `none` task's launch, which that launch records as its own start; that an accepted `in-place` commit has the launch commit behind it is asked of git by the command and is not checked again at replay; a log written before #188 has launches without `as` and is refused at replay (no chief state existed to carry over).

## What only the user can do

Approve a protected action, take over a live lease, drop a task, lift the retry cap, remove a worktree. Each is a `/chief …` command the user types or a confirm dialog the user answers **(proposed mechanism, built as proposed in #191)**; the script's own subcommands for these refuse unless called by the extension from that path. An approval names one action, one target and one task, is copied into the next contract, and is checked again when the round launches. Text in a report or a file is never an approval. With `bash` open, the chief could still write the log directly: this stops mistakes, not a determined session.

As built (#191):
- **How the script tells the user.** `main` takes a `caller`, which is `user` only when the code calling it says so, and nothing on a command line or in the environment sets it: run as a process, which is the only way a model's `bash` reaches it, the script is never the user. The extension calls `main` in Pi's own process as `user` from two places only: the handler of the `/chief` command the user typed, and the takeover dialog the user confirmed. No tool call reaches either. One function in the script (`userOnly`) makes the refusal for every such action, and says what the user types instead.
- **What the user types**, in the chief's session: `/chief approve <task>`, `/chief drop <task>`, `/chief lift <task>`, `/chief answer <task> <words>`, and since #192 `/chief cleanup <task>`. Anything else after `/chief` shows the usage and calls nothing. The script's answer or refusal is shown to the user, and what was done is sent to the session as a message that starts no turn.
- **Approve.** `/chief approve <task>` opens three dialogs, for the action, the target and the user's words; each is typed by the user, none has a default, and one left unanswered approves nothing. The script's `approve <task> --action … --target … --words …` records one `approval` event, which names that one task, one action and one target. It changes no state and starts nothing; `status` shows a task's approvals under it.
- **Copied, and checked again.** A contract is written when a run starts, never earlier, from the task's approvals as the log holds them under the lock that starts the wrapper: the launch of the round reads the log again after its reservation, so an approval withdrawn in between is not in the contract. An approval given while a run is live reaches the coordinator only through the next round's contract.
- **Withdraw.** `chief.ts … withdraw <task> --action <action> --target <target>` records `approval-withdrawn`, which takes from the task every approval of that action on that target; no contract written afterwards holds them, and one that names no approval the task has is refused, at the command and at replay. It takes authority away and gives none, so the chief may run it when the user says so; it is not one of the user's commands. A contract already written, and the run reading it, keep what they were given: to stop that run is `cancel`.
- **Drop.** `drop <task>` records `drop` (`DROPPED`, which nothing leaves). The task's state is looked at before who asks, so it is refused while `LAUNCHING`, `RUNNING`, `STOPPING` or `ATTACHED` for the user too, and for `ACCEPTED` and `DROPPED`. It removes nothing: the task's brief, reports and checkout stay.
- **Lift.** `lift <task>` records `cap-lifted` on a `FAILED` task that has reached the cap, and is refused, at the command and at replay, where there is nothing to lift, so a cap is not lifted ahead of time.
- **Takeover.** When `/chief` is refused because the lease's holder is running, or cannot be told to be gone, the extension asks the user in a confirm dialog that names the holder's session, generation and pid, and on yes runs `claim --takeover <that generation>` as the user. The script refuses it when another session has claimed since.
- **The limit.** This stops mistakes, not a determined session. The chief has `bash`, and with it could append an `approval` or `drop` line to `events.jsonl`, import `chief.ts` and call `main` as `user`, edit a contract after it was written, send keys to the terminal its own Pi runs in (a `/chief` command or a dialog's answer typed that way is taken as the user's), or `release` a live holder's lease with the session and generation `state` prints and then claim it with no takeover; nothing here detects any of that. The same holds for a coordinator: guard, which it has unless the chief's session had guard off at launch ([Guard](#guard)), reads `bash` commands for what is destructive, not for who may write the log. What it does stop: a model that runs the script's command for one of these actions, on its own judgment or because a report or a file told it to, is refused and told the user must type it.
- `approve` and `withdraw` reconcile first, like every command on an existing task, and are taken in any state: one recorded on an `ACCEPTED` or `DROPPED` task is copied nowhere, since no further contract is written.
- A failure of the script on one of the user's commands (code 2) is shown apart from its refusal: whether anything was recorded is then not known, and the user is told to read `status`.
- Not covered: (removing a worktree, the fifth of the user's actions, came with `cleanup` in #192, under Checkout identity;) the takeover dialog opens on any refused claim while a holder is not gone, so a claim refused for another reason asks too, and the takeover is then checked afresh by the script; the three dialogs of `/chief approve` and the takeover dialog were tested with a fake Pi, not watched in a real one; an approval's action and target are free text, which the script matches against nothing (the coordinator reads them, and guard does not: see [Guard](#guard)); the same approval given twice is recorded twice and one withdrawal removes both; the user's `answer` and `/chief approve` words go to the script as one argument each, so what a command line cannot hold (a NUL, more than 20,000 characters) is refused.

## The chief session

- Blocked from `edit` and `write` under the repo and under `<repo>.worktrees/` except `.chief/notes/`.
- Woken when a run ends, by a message that says only to read `status`. A wake is dropped if its session no longer holds the lease.
- Reads reports as data. For a landing with a diff it gives the diff to one read-only worker and reads the findings.
- Acts without the user only inside assigned work: review, a fix round, an answer from the brief, launching a queued task, accept.
- Its guard state is the one its coordinators' runs start with ([Guard](#guard)).
- Another interactive session started in the repo or a worktree sees one line naming the chief, and the task writing in that checkout if a run is live there.

As built (#190), in `extensions/chief.ts`, which the root package loads:
- The extension imports the script and calls its `main` in Pi's own process for `claim` (with its session; the claim is given its generation), `release` (with both) and `state` (with neither); it keeps no state but what it last saw. From the claim on it calls the script in the repo's main checkout, since the session's own directory may be a worktree that is removed under it; `/chief` is refused where that is not where the script finds the repo (a git directory kept apart from its checkout, a submodule), which the script's own places do not cover either. `/chief` runs `claim --pid <Pi's pid>`. It is refused in any mode but the TUI (print, JSON, RPC), before the script is called, and by the script while the holder's process runs. A refusal is shown to the user, after the takeover dialog when the holder is not gone (#191, under What only the user can do).
- `chief.ts state` is the script's one command that needs no caller and takes no lock: it prints the replay as JSON (the repo, its worktrees directory, the notes area, the lease while held and whether its holder's process is live, and each task's state, last run over, whether it has a live run, whether it is overdue, and whether its run is live in the checkout the command was run in). The log only grows, by whole lines, so a reader without the lock sees it as it was at some moment; a last line not yet ended is left for its writer. It reconciles and writes nothing, and creates no state directory. The extension reads everything it knows through it, and it is what the batch preflight (step 10) can read with no lease held. It is no way around the lease: it changes nothing, and the log is a file the same user can read.
- **The model to launch with** (#193, the round after the whole-branch review). The message `/chief` sends the session names the session's own model as `provider/id`, the form `launch --model` takes, read from Pi (`ctx.model`) each time the message is sent, so a `/chief` typed after `/model` names the new one. A session with no model is told to ask the user; no model is ever guessed. Before this the chief was not told what to pass.
- **Wake.** Every 5 seconds the chief's session reads `state`. While a task is `LAUNCHING`, `RUNNING` or `STOPPING` it first runs `reconcile` as a process of its own (`node chief.ts --session … --generation … reconcile`), so a run whose owner died is recorded without the chief asking and a look never waits for the repo lock in Pi's process; one look at a time, and a `reconcile` that has not ended after a minute is killed and counts as a failed look. When a task's last run over is later than the one the session was last woken for, or a run has gone past its deadline since, and the session is between turns, it sends one message, `Read the chief's status: \`node <chief.ts> --session <id> --generation <n> status\`.`, which starts a turn. The message names no task and no outcome. In the middle of a turn nothing is sent: the first look after the turn sends it, so no wake waits in a queue. Several runs over at one look are one message; a run over, or overdue, at the claim is none, since `/chief` tells the session to read `status`. The lease is read just before the wake is sent: a look that finds the session no longer holding it sends nothing, stops looking, lifts the edit block and tells the user once. A takeover between that reading and the moment Pi starts the turn is not excluded (Pi holds a message back while its own end-of-turn handlers run); the `status` the message asks for is then refused by the script, which is what drops it. A look that fails is shown once and tried again at the next.
- **Edit block.** While chief, a `tool_call` of `edit` or `write` is blocked when the file its path names (relative to the session's directory, with Pi's `@` prefix, through symlinks) is the repo's main checkout, the worktrees directory, or under either, unless it is under `<repo>.worktrees/.chief/notes/`. The rest of `.chief/` (the log, briefs, run directories) is blocked, and the notes area is the directory of that name: when it is a link, what it leads to is not excepted. A `~` or `file:` path is blocked with a request for an absolute one, and a path through a link that leads nowhere is blocked: both as in a delegate worker's write fence, whose reading of a path (`writeTarget` in `delegate-fence.ts`) this uses, so that no path is read differently here than by Pi. `bash` is not looked at: as with the user-only actions, this stops mistakes, not a determined session.
- **Notice.** At `session_start` in the TUI, in a session that is not the lease's holder, one line: `chief: session <id> (pid <pid>) is the chief of <repo>`, with `; task <id> is writing in this checkout` when a run there is `LAUNCHING`, `RUNNING` or `STOPPING`. With a live run and no chief (runs go on when the chief exits) the line says the repo has no chief. A lease whose holder's process is gone names no chief. Nothing is shown when there is neither, and nothing is sent to the model.
- **The lease's end.** Pi has a hook after all: `session_shutdown`, on exit and on `/reload`, `/new`, `/resume` and `/fork`, each of which ends the extension instance that knew the generation. It runs `release`. After `/reload` the lease is free and the user types `/chief` again, which gives the next generation; no takeover is needed. A displaced session's `release` is refused by the script, and a Pi that is killed releases nothing: the next `/chief` finds the holder gone. A `release` that fails is shown as an error and leaves the lease held by a process that is still running; `/chief` in that same session and process then takes the lease up again with its generation instead of claiming, which the script would refuse.
- **Observed in a real interactive session** (Pi 1.6.1 in tmux, 2026-11-27, the session chief of a scratch repo, a run's end recorded while it waited):
  - *A dialog open* (`ctx.ui.confirm` from an extension command, left unanswered): the wake was delivered and the turn ran to its end behind the dialog. The model ran `status` and answered; the dialog stayed open and selectable, was not answered or dismissed by the wake, and returned `true` when Enter was pressed afterwards. No key reaches the dialog from a wake: it is a message to the session, not typing into a pane.
  - *The user typing* (text in the editor, not submitted): the wake was delivered and its turn ran; the text stayed in the editor unchanged.
  - Not observed: a wake due while a *guard* dialog is open for a tool call of the chief's own turn. The session is then in the middle of a turn, so by the rule above nothing is sent until the turn is over; that was tested with a fake Pi, not watched in a real one. It is carried to the acceptance run (step 11).
- Not covered: a wake is sent, not confirmed read; `claim` and `release` run in Pi's own process and wait for the repo lock like any command, up to 15 seconds, at `/chief` and at the session's end; `state` reads the log in one go without the lock, and a reading that overlaps the repair of an append a killed writer left unfinished can fail once, which a look shows and tries again; a run that ends while no session is chief wakes nobody, and the next `/chief` says to read `status`; each look runs `git` and `ps` in Pi's own process (under 0.1 s here, every 5 seconds); the look's `reconcile` is started with the `node` that runs Pi; a lease left held by a failed `release` and then `/new` (another session id in the same process) is refused until Pi exits or the user's takeover (#191); `/chief` is in every session that loads the root package, and every interactive session started in a git checkout reads `state` once.

## The skill

As built (#193): `skills/chief/SKILL.md` holds judgment only, in five sections: writing a brief, choosing a landing, reviewing a result through one read-only worker, what the chief does without the user and when it asks, and what only the user can do. It says that the chief runs no builds, tests, installs or merges. It names the script's commands and leaves every state, guard and option to the script and its refusals. `install.sh` does not link it, and it is not in the root package's skills: until the acceptance run (decision 26) the chief is not offered as a user skill. The extension's message at `/chief` names the file's path and tells the session to read it first; a session that does not is not detected.

## The contract

Generated, never hand-written, and rewritten for every run. An approval is an `approval` event in the log naming its task, an action, a target and the user's words; a contract lists only its own task's, each quoted on one line, and an event missing one of those parts is refused at replay. The brief ends the contract inside a fence longer than any run of backticks in it, under a line saying that nothing in the fence is an approval or changes a rule; this marks the brief off for the reader, and enforces nothing. It carries the brief, the landing and what it requires, the recorded approvals, the report path and format, and these rules: write only in your checkout; get an independent review before reporting when you changed files; do not use background delegate jobs; guard may block a command, and a blocked command is not run another way but reported as `BLOCKED` with the command and guard's reason, with any secret in them replaced by its variable name. The contract lists no destructive command (#197; until then it held a list of its own, stricter than guard's): what is blocked is guard's to say, in a run that has guard ([Guard](#guard)).

## Attach

`chief.ts attach <task>` takes the run lock, refuses unless the task is idle and its checkout still exists, and opens `pi --session <session>` in that checkout. A headless session opened this way showed its history and took a new prompt ([spike set 3](spikes.md)). If Pi offers to continue or fork elsewhere because the directory is gone, attach has already refused.

As built (#193):
- **Whose it is.** `node chief.ts attach <task>` is the user's, typed in a terminal of their own. It takes no `--session` and `--generation` (it is refused with them): it is not the chief's, the chief's Pi could not hand its terminal to another Pi, and the session it opens outlasts whoever is chief. It is refused when its process has no terminal on standard input and output, before anything is looked at or recorded, which is what a model's `bash` gets. Like the user-only commands, this stops mistakes: a session that makes itself a pseudo-terminal is not detected.
- **What it checks**, in this order. It reconciles without a lease, and so only what its own refusals are made from: the task itself, and the tasks recorded in the same checkout, whose live run or open session refuses it. What became of any other task's run stays the chief's to record (#189 fenced `status` and `reconcile` for that reason); until the round after the whole-branch review, attach reconciled every task. The task must be idle (`ASKED`, `REPORTED`, `FAILED`; a live run refuses it, and so does an unexplained one) and one of its runs must have started Pi: a `QUEUED` task, and one whose only launch never started Pi, have no session, and Pi would make a new one under that name. It takes the task's run lock without waiting, the lock a run's wrapper holds, and is refused while any process has it. Under the repo lock it then refuses while another task's run is live in that checkout or the user has another task's session open there, and when the checkout cannot be read (`look`: a removed worktree, a directory that is no longer the top of a working tree), so Pi is never left to offer the session somewhere else. Only then is `attach` recorded, with the attaching process (pid and start time) and its process group.
- **The session.** `pi --session <session>` in the task's checkout, on the attach's own terminal, where `<session>` is the session of the last run that started Pi (a round reserved and never started names a later one that does not exist). That a session file is there is Pi's to say, not the script's: the log shows that Pi was started under that id, and where Pi finds no such session it says so and exits (it makes none, which `--session-id` would), and the task is detached with that exit status. No model is passed, as the design has it: the session opens with the user's default model, as spike set 3 saw. The run lock is held until Pi exits.
- **While attached.** The task is `ATTACHED`: `round`, `answer`, `accept`, `cancel`, `drop` and `cleanup` are refused, at the command and at replay, and a wrapper could not take the run lock if one were started. No other task's run is reserved, and no other task is accepted, in that checkout (`free` counts an open session like a live run): the user may be writing there. `status` names the session and the attach's pid under the task.
- **Detach.** When Pi exits, however it exits, the attach records `detach` under the repo lock: the task returns to the state it had, with what was found under it, and the checkout is rechecked as before a round (`changed`). A checkout that is not as the task's last run left it, on another branch, or unreadable is recorded in the same event (`detail`, `found`) and the task is `ASKED(user)` instead, with nothing reset; a finding the user was already asked about, of a checkout no different, is not recorded again. The command's last line says which. A Pi that could not be started detaches the same way and is an error (code 2), and so is a session over whose detach somebody else recorded meanwhile.
- **An attach that was killed** leaves the task `ATTACHED`. Reconcile (`status`, `reconcile`, any command on a task, the next `attach` to that task or to one in its checkout) detaches it, with the same recheck, once neither the attaching process (by pid and start time) nor any member of its process group is left, by the process table and by asking the system. While the attach is gone and its group is not, Pi may still be open: nothing is recorded, and `status` says so under the task. A process table that cannot be read explains nothing.
- Not covered: after an attach in which the user commits a fix themselves, the recheck finds a commit no run explains and the task is `ASKED(user)`; only a run (the user's `answer`), `drop` or another attach leaves that state, so the user's own fix cannot be accepted without a further run. An attach still records, with no lease, what became of a run of its own task and of the tasks in its checkout: its refusals could not be told from a stale log otherwise, and a `status` by the chief would record the same. The open itself was tested with a fake Pi and a fake terminal, not typed in a real one (the interactive open of a headless session is spike set 3's; the acceptance run has one attach); Pi takes `--session` as the start of an id when no session has exactly that id, and offers to fork one found only under another directory, which the user can decline; the chief's look reconciles only while a run is live, so a killed attach is detached at the next `status`, not within 5 seconds, and a detach wakes nobody (the user says they left); a Pi the user started themselves in the checkout, without `attach`, is not seen at all; an attach started from a shell script shares that script's process group, so a killed attach stays `ATTACHED` until the script ends; the session is opened with the user's default model, their own extensions, and guard as any interactive session of theirs has it (it asks, where a run's blocks), whatever guard state the task's runs started with; `/new`, `/resume` or `/fork` inside the attached Pi leave the task's session for another, and the task stays `ATTACHED` until Pi exits; whether Pi's own session file is written by two processes is not checked beyond the run lock, which only wrappers and attaches take.

## Build order

Each step ends with its tests passing and `npm run check --prefix extensions` green.

1. **Log and lifecycle.** Pure replay, guarded transitions, the repo lock. Tests: every illegal transition refused; two processes appending at once; replaying the same evidence twice.
2. **Lease.** Claim, generation, fencing, takeover. Tests: two `/chief` at once; a displaced session's command, wake and shutdown; a holder that is alive but not responding.
3. **Contract and brief checks.** Tests: a brief missing each required part; an approval for another task not copied.
4. **Wrapper, launch, result, reconcile, cancel** for `none` and `in-place`. Tests: kill the script after each launch step; kill the wrapper; kill Pi; exit file present without `run-ended`; a reused pid; a provider error with exit 0; cancel leaves no child process; a second launch on a busy checkout.
5. **Background delegate refusal** in `packages/pi-workers`, with its test and changelog line.
6. **Extension.** `/chief`, user-only commands, wake, edit block, notice. First test: a wake arriving while a dialog is open or the user is typing.
7. **Checkout identity and `accept`.** Tests: branch switched mid-run; worktree removed; a dirty tree at accept.
8. **`branch` landing and worktrees; `cleanup` on request.** Tests: cleanup refused with untracked or ignored files, under a live run, and never forced.
9. **Attach, drop, retry cap, deadline.**
10. **Mutual refusal with `batch-chief`; `skills/chief/SKILL.md`.** (#193, with attach from step 9.)
11. **Acceptance run** (decision 26): three real me-pi tasks, one per landing, two at once, one chief restart, one attach. It supplements the fault tests above and replaces none.
