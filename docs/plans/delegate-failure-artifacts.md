# Failed-tool diagnostic artifact: implementation spec

## Goal and constraints

Capture enough attributable evidence to diagnose failed implement-worker tools (including targeted tests/builds, not only the declared `check`) without retaining a worker/session transcript or changing check semantics. Preserve existing `check.status`, `check.runs`, stale-on-edit rules, WIP/finish behavior, and all original details artifacts. Keep this private and scoped to one implement job (`im<n>`); do not enable it for read-only roles. The bg7/im5 recovery report establishes the gap: tool starts/ends are consumed in memory, `trackCheck` stores only command plus `isError`-derived status, and tool result bodies/full-output references are discarded; Pi's outer worker stderr is not child Bash stderr.

## Proposed design / smallest robust format

Use **one versioned JSON artifact per implement job**, e.g. `<tmpRoot>/me-pi-delegate-<parentPid>/<imN>-failed-tools.json`, owned by the existing job and written mode `0600` inside its existing `0700` directory. Do not overwrite/delete the existing `<imN>.md` or answer artifacts. A top-level `{version: 1, jobId, entries, capture}` object is sufficient; each entry is one failed tool call, with: attempt index/requested model; `toolCallId`, `toolName`; start/end ISO timestamps and elapsed ms only when observed; command provenance object (`rawArgs.command`, `effectiveCommand`, plus provenance state); `isError`; numeric exit code only when present in structured tool result; bounded output/child-diagnostic text and references; and explicit `missingFields`/`truncated` markers. For non-bash tools retain a bounded serialized result summary, not arbitrary tool input. Keep original command, effective command and result output separately; never infer/claim effective command from raw args. If Pi's event schema does not expose a true effective command or exit code, record null plus `not-provided`, not a guessed value.

Suggested caps: at most 100 failed calls/job, 64 KiB per output text, 512 KiB total artifact, and a bounded (e.g. 20) child diagnostic/full-output references per call; truncate at UTF-8 boundaries and record exact retained/original byte counts when known. On cap overflow stop adding payload but preserve a capture-level `truncated: true` and counts. Keep `full_output_path` as a reference only; do not read/copy arbitrary referenced files in this change. Preserve it only after path redaction; state clearly if missing/unavailable. A future retention policy can clean artifacts explicitly; do not silently prune prior jobs as part of capture.

## Data flow and file seams

1. `extensions/delegate.ts`: replace `calls: Map<string,{tool,command}>` with a minimal call record captured from `tool_execution_start` (ID/name, raw input command, start timestamp). At `tool_execution_end`, first keep current `trackCheck(...)` invocation/semantics unchanged, then pass the pair into an implement-only bounded collector. Match by ID; missing IDs/starts/endings are surfaced in capture metadata, including unclosed calls on cancel/termination. Capture failures for every tool name when `isError` is true, regardless of `isCheckRun`; do not treat an overall worker/model failure as proof a tool failed. Extract result output, numeric exit status, `full_output_path`, and any child diagnostics only from actual event/result fields, marking absence explicitly.
2. Add a small helper module (recommended `extensions/delegate-artifacts.ts`) for typed record construction, explicit redaction, UTF-8/aggregate caps, and safe JSON writing; unit-test this independently. Redact **before any artifact persistence**, including command, cwd/path strings, outputs, error messages, and full-output refs. Use only documented explicit patterns (e.g. common credential assignments, bearer/token strings, known secret path forms); label artifact `redaction: explicit-patterns-v1; not guaranteed complete`. Do not inspect environment contents, credential stores, auth files or unrelated sessions. Do not claim perfect redaction. Also sanitize control chars in human-readable details/handback.
3. Job-scoped collector is initialized from `implement.job.id/tmpRoot` (or the existing job directory) and remains in memory only for the worker attempt; pass its final artifact path/state through `RunResult`/`Outcome` to `finish`. Ensure fallback attempts are distinguished. On cancellation, finalize captured failures and mark calls with no end as `end-not-observed`; never manufacture child exit status. A missing/rewritten raw command remains visible as raw input; effective command is only recorded when Pi supplies it. A start/end mismatch is a missing-field condition, not grounds to discard other entries.
4. `extensions/delegate-implement.ts`: extend `Outcome`/`Facts` with optional artifact reference and capture status. `writeDetails` adds a short section linking the JSON file and reporting capture/truncation/unavailable status; `formatHandback` should add a concise diagnostic reference on failed handbacks without dumping output. Ensure no artifact is created on successful runs with no failed tool calls (unless needed for explicit capture status), and preserve current two-line successful handback shape.
5. I/O: create job directory with `0700`; create artifact exclusively/atomically with `0600` (temp file + rename or exclusive open, ensure existing files are never replaced); detect write/rename/permission/size failures and surface them in details/handback and outcome. Do not let capture I/O errors alter tool result, check state, worker exit, or turn a passing check into failure; surface a loud `capture unavailable` warning so diagnostics are not silently lost. Existing `finish` already treats details-write errors as problems; decide separately whether failure to write a new optional diagnostic artifact is a finish problem: recommended **do not change gate outcome**, but emit a visible warning and record it in details when possible.

## Material decisions and risks

- Raw versus effective command distinction is non-negotiable: current code stores raw `event.args.command`; it cannot establish shell-expanded/effective command. Capture actual tool result metadata if present; otherwise say unavailable.
- A numeric exit code may not exist in Pi's event model; retain `isError` independently and never synthesize `1` from it. Child output may itself be absent or live only in an unlinked temporary file. `full_output_path` is provenance, not proof the referenced file still exists.
- Pattern redaction is best-effort and can miss secrets, especially arbitrary values in output/commands; artifact remains sensitive. It must never be described as safe for public sharing. Bounds limit exposure and disk use, not sensitivity.
- Cancellation can prevent an end event; finalization must not change cancellation or check outcomes. Process-level loss/crash before artifact flush remains a residual gap.
- Output capture is diagnostic-only: errors in capture/storage must not mutate `check.status`, commit/WIP policy, or passing gate. Visible warnings may make an otherwise successful result operationally concerning, but must not recast it as a failed check.
- Retention: recommend keep existing temp lifecycle (no automatic deletion of historic artifacts); owner-only permissions and bounded per-job size. This leaves disk accumulation as an explicit residual risk; later retention cleanup needs separate design/approval.
