# Use and recover delegate workers

The `delegate` tool starts child `pi --mode json -p` workers. A worker sees the task you pass, not the main conversation, so include the relevant paths, context, and acceptance criteria. Ask Pi in ordinary language, for example: “Have a scout trace how this retry path works and return path-and-line evidence.” Read-only workers cannot run shell commands; the coordinating session must supply any needed command output or diff as a file path. Installation, package filtering, and the separate `guard` and `Skill` extensions are covered in the [README](../README.md).

## Roles and tools

- `general` is the default for read-only local investigation. `scout` is a short local lookup with path-and-line evidence. `review` returns severity-ranked findings for the supplied material.
- `research` gathers web sources; `challenge` stress-tests a premise. Both enable web tools by default and require the separately installed `pi-web-access` extension; me-pi alone provides no web tools (the optional full setup installs the unpinned npm package; to install that extension alone, run `pi install npm:pi-web-access`). Other roles can request web tools with `web: true`; `implement` cannot. Web-enabled workers read project files as well as fetched pages: enable web only when outside sources are needed, and treat fetched content as untrusted data.
- All roles except `implement` are read-only by default. `output: true` adds only the `write` tool, restricted to that worker's fresh private directory under the OS temp directory; the result reports its path. It grants no `edit`, Bash, or writes to other temporary paths. The main session must review and copy any draft it wants to keep.
- `implement` is the only role that edits the checkout. Its `edit`/`write` paths are restricted to the real checkout, excluding the Git common directory. It requires a clean Git tree on a branch other than `main` or `master`; worker checks block ordinary `gh` and Git push commands. Give it one unchained `check` command; the worker runs it alone, exactly as given, after its final edit, and commits there. A worker run of the check inside a pipe, chain, or redirect is blocked, since its exit status would not be the check's.

Workers load the same `GLOBAL_AGENTS.md` and repo `AGENTS.md` as the main session, minus policy they cannot use: every worker drops `## ` sections whose heading is marked `(coordinator only)`, and read-only workers also drop those marked `(coordinator and implement only)`. Mark a new policy section the same way when it governs only the coordinator or writers.

Workers cannot delegate; a handback completes only the assigned step. When a skill applies, the coordinator retains its required user decisions and orchestration through completion, including any independent review the skill requires.

## Choose and close work

First honor explicit user-required delegation and any delegation or independent review required by the repo or an applicable skill. Otherwise, delegate bounded, independently checkable work when context savings, parallelism, or independent judgment justify briefing and verification costs; keep coupled decisions with the coordinator. Give each worker a compact, self-contained brief covering scope, deliverable, relevant context and constraints, acceptance evidence, and how to report blockers.

A multi-model panel (`runs`) repeats the same task for each model; decompose work into separate calls with separate briefs. Treat partial answers as incomplete. Explicitly accept, reject, or recover each handback; verify decisive claims proportionately, inspecting implementation diffs and check adequacy without routinely repeating worker work. A final failed or stale declared check, timeout/unknown effect, and WIP commit stay incomplete. An earlier ordinary Bash failure may be repaired within the current worker run ([failure provenance](#failure-provenance)); that is not replay or continuation authority, and the final handback still needs a fresh passing check and normal committed delivery. Live UI acceptance requires actual observable evidence from the running interface; static inspection alone does not establish it.

### Coordinator artifacts and verification

The coordinator owns the task ledger and reports outside the checkout. Give workers read-only paths to those artifacts and ask for handbacks, not ledger/report writes; do not relax the implement write fence to accommodate coordinator artifacts. The coordinator records scope, acceptance evidence, the exact declared check, review coverage, and handback/finding dispositions.

Before dispatch, estimate the check/build cost from previous runs or the task's likely verification work and reserve time for verification and a usable handback inside the worker's wrap-up window ([limits](#limits)). There is no universal minute cutoff. Split work likely to exceed about 1,500 changed lines into frozen slices before its first dispatch, and have workers bound focused test runs with a per-test timeout while iterating; in the piops run, hanging test runs, not code, spent most of the 45-minute attempts. Stop starting new behavior when the remaining window is needed for verification and handback. An ordinary failed check does not prohibit repair: within the approved scope and remaining budget, fix the cause and rerun. Any relevant edit after a passing check, including formatter or hook writes, makes the affected evidence stale until rerun; passing results must describe the delivered source.

Choose verification at the strongest supported seam that answers the task, exercising the real owner or event seam rather than a mock mirror, and record what the chosen evidence catches and misses. This evidence-driven default needs no routine user approval of internal test seams and does not load `tdd` or require red-first work. An explicit user or repository test-first/red-first requirement for the task overrides that default: load and follow `tdd` for that requirement.

### One writer and frozen review

Keep one checkout writer, including coordinator writes. Use remaining capacity for independent readers within the four-worker limit; do not add concurrent worktree writers or session/clone workarounds. Wait for the active writer's handback before editing, running Git write commands, or starting shared verification in that checkout. Review a frozen source snapshot: identify its commit or captured diff and baseline, and keep the source stable while reviewers inspect it. The coordinator runs shared checks or Compose only against stable source, never while a writer is changing it.

### Review coverage and closure

Map critical requirements to end-to-end acceptance evidence at the first usable integration point. Request focused independent review when risk warrants it, not after every worker, and do not add a mandatory panel. At final integration, independently review the whole delivered result with separate **Standards** (repository coding standards) and **Spec** (the originating requirements) axes; honor any applicable skill's full review requirements.

The coordinator dispositions routine findings without asking for approval one finding at a time: record required fixes and verify them, reject findings with evidence, or record justified maintenance deferrals that do not waive required acceptance work. Ask when ambiguity changes implementation or a decision requires new authority; required missing work stays incomplete. For a recurring defect class, inspect analogous sites only within the affected owner/scope.

After local fixes, affected-delta closure names the changed source, affected requirements and checks, and the prior Standards/Spec coverage explicitly carried forward. It is not a full-skill review. Reopen broad review for semantic changes, migrations or cross-owner effects, uncertain impact, regressions in previously covered behavior, or an explicit user request. Every invocation of the full review skill still covers both axes. Stop review rounds when current source is fresh-green, required findings are verified, both axes cover delivered behavior, and maintenance judgments have recorded dispositions; do not require endless clean rounds.

### Standing bounded coordinator recovery — LOAD-GATED

**Current authority boundary:** the user-approved deletion of `GLOBAL_AGENTS.md` in `a2d3e79` removed that file's former blanket stop-on-any-guard/worker-limit clause; its absence grants no standing recovery authority. Per-invocation guard and resource limits remain enforced. Another attempt has exactly two routes, both only after trusted worker termination, effect, checkout, and fixed-slice allowance reconciliation:

- **Standing A4:** a qualifying loaded A4 session may handle ordinary repairs/findings and a reconciled worker-limit continuation within the original authority, same selected eligible model, and remaining allowance without a new routine approval.
- **Task-specific:** If any standing gate is absent or unverified, proceed only after the user explicitly approves that particular bounded continuation; this route does not activate standing A4.

**Load gate.** A4 is coordinator/skill policy, not runtime security: runtime does not enforce aggregate slice counters or authenticate consent. It is active only in a session where the separately approved global policy, supported provenance-capable runtime, and matching reviewed skills are installed, loaded, and revalidated, and every activation gate is satisfied: A0-live safely loaded; A1/A2/A3 complete with passing A2 provenance checks (necessary, not sufficient); frozen final independent Standards/Spec review of the whole result with required findings closed; the approved runtime/code/tests/guides/policy and applicable skill available; separate user approval; and the authorized main-session policy update, install, and reload, followed by affected-delta review and check. If any prerequisite is absent or unverified, standing A4 is **INACTIVE** in that session. Reading newer prose cannot grant a stale session authority; the session must be reloaded and revalidated.

**Envelope (both routes).** Before the first attempt, predeclare and freeze one immutable planned slice: identity, scope, acceptance evidence, and declared check. It allows one initial attempt plus at most two reconciled continuations (three attempts total), each on the same selected eligible model under the original task-data/provider authority; no pool-candidate switch, account/provider evasion, or authority reset. The coordinator-owned ledger keeps the slice's original origin/base and every attempt base; relabeling, splitting, changing job IDs, or advancing bases never resets the allowance, and no attempt may suppress an earlier hook or reuse expired allowance. Each attempt retains the 45-minute hard limit, nominal $5 cap, and tool-call limits: at most 135 allocated hard minutes plus possible termination/finalization overhead, not an exact elapsed ceiling or billing guarantee. A continuation preserves scope, acceptance, WIP/history, and the originally authorized data classes, providers/models, and destinations; it grants no new authority.

**Stops and progress.** A guard-denied effect remains denied: never retry or relay a denied substantive effect through another tool, worker, provider, path, session, or the coordinator. Omit optional work only when optionality was predeclared and trusted evidence proves non-execution; required work remains incomplete until its acceptance evidence, fresh check, and normal committed delivery are reconciled. Unknown or partial effects prohibit replay. Unknown/partial effects, integrity uncertainty or sensitive integrity effects, missing prerequisites, and exhaustion stop affected writes and acceptance; a passing check does not erase them. Continue only separable authorized work; accept an unchanged checked commit only while its check evidence remains fresh; write any coordinator report only under pre-existing authority from allowed source evidence. Compare state, usable evidence, and verified findings: useful WIP can count as progress without a fresh green check, while a repeated reason alone does not establish no progress. Halt and record the evidence when allowance is exhausted or no observable progress is shown. When the load gate is satisfied, ordinary stops trigger no repetitive human prompts; seek a human only for new authority, consequential choices, or unresolved safety. This does not replace the mandatory final integrated independent Standards/Spec review followed by affected-delta closure, and adds no per-job review panel.

**Normative coordinator walkthroughs—not runtime tests or aggregate enforcement:** first-attempt success ends the slice; two continuations exhaust it; relabel/split/job/base changes do not reset it; useful reconciled WIP is progress without green; repeated reason alone is inconclusive; timeout requires termination and state/effect reconciliation; unknown/partial effects block replay; optional denial requires predeclaration plus trusted non-execution while required denial stays incomplete; an unchanged commit is acceptable only with fresh check evidence; human approval is reserved for new authority, consequential decisions, or unresolved safety.

## Configure model pools

Optional model pools live at `~/.pi/agent/delegate.json`. Without a file, workers use the main session's model and thinking level; `scout` thinking is capped at `low` (or remains `off`).

```json
{
  "version": 3,
  "scout": {
    "models": [{ "model": "provider/scout-model", "thinking": "low" }]
  },
  "worker": {
    "models": [{ "model": "provider/worker-model", "thinking": "medium" }]
  },
  "review": {
    "models": [{ "model": "provider/review-model", "thinking": "high" }]
  }
}
```

Optional top-level `readOnlySkills` (v3 only) lists the skills read-only workers see in their prompt and can load with `Skill`, for example `["code-review", "codebase-design", "diagnosing-bugs", "domain-modeling", "research", "writing-for-agents", "pr"]`; without it they see all discovered skills. `implement` always sees all. A listed name that Pi did not discover is ignored.

Replace the example IDs with provider/model IDs available to your Pi installation. Each entry needs a `thinking` value: scout entries accept `low` or `off`; worker and review entries accept `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`. Optional pool-level `thinking` sets the level for models without a per-model entry; if omitted, the session level is used. `review` is optional: when omitted, `review` calls use the `worker` pool; when configured, it is the default pool for `review` only (`general`, `research`, `challenge`, and `implement` keep using `worker`). Pools are role defaults, not allowlists. Entry order selects the default model but is not a failover sequence: only the first candidate is dispatched.

For a one-off choice, the coordinator can set either or both fields in a run, for example `runs: [{ model: "provider/model", thinking: "high" }]`; one-off choices never modify `delegate.json`. An omitted model selects the first candidate in the role's pool, and an explicit thinking level applies to that candidate. An omitted thinking level keeps the configured per-model default, then the pool-level default, then the session level. Any explicitly named model runs alone and never falls back to another model, even if it is listed in the role's pool. When a non-review role explicitly names a model that appears in the `review` pool, the role's own pool entry for that model still wins if present; otherwise the documented per-model thinking default applies, and for an unlisted model the role's pool-level default and then the session level apply. Naming a cross-pool model does not inherit review-pool thinking or change role-pool precedence. An unlisted model must be an exact Pi catalog ID in `provider/model` form that Pi's model registry reports as available with usable authentication; the tool resolves no human-friendly names. Scouts remain capped at `low`, or `off` when requested.

**Cross-model fallback is deferred** until Pi supports effective-endpoint enforcement at the fresh child's request boundary and positive scope/budget tests pass. The parent registry snapshot cannot bind the child's effective endpoint; no credentials are read to try to prove otherwise or for endpoint checking, and model/provider authority is not changed. Current first-only dispatch makes no endpoint or run-scope enforcement claim. The coordinator continues to own user consent: the delegate infers no approval from a pool, a typed object, a retry event, or registry metadata, and never selects a different provider on the coordinator's behalf. The legacy `fallbackAuthorization` input is scope intent only and does not enable or authorize a destination. A structured `auto_retry_start` event is retained as provenance and yields an explicit cross-model-fallback refusal diagnostic; it does not start another candidate. Quota/billing errors, ordinary unavailable-model messages, and shell-command `429` output are not endpoint evidence or fallback authority. Existing deadlines, budgets, provenance, and safety stops still apply to the single dispatched candidate.

Edit the JSON yourself, then `/reload` to reload the extension. `/delegate models` shows the config path; `/delegate status` shows pool availability and missing tools.

## Run and stop work

For a long task, ask Pi to use `background: true`. It returns a `bg<n>` job ID; `/delegate status` shows running IDs and recent calls, and `/delegate cancel <id>` requests cancellation. For calls with worker entries, status also shows the stage and each active worker's short model name, thinking level, elapsed time, (for multi-worker calls) worker index, and latest sanitized tool name when available. `/reload`, session replacement, or Pi exit ends background jobs; wait for them before reloading when possible.

For an external supervisor that watches a file rather than the pane, set `ME_PI_STATUS_LOG=<path>` before starting Pi: when a coordinator turn ends on a provider error after Pi's own retries, the extension appends one `<ISO time> STOPPED: <infra|account|model/task>: <error>` line (account limits add `(BLOCKER: needs the user)`). Set `ME_PI_SPEND_BUDGET_USD=<n>` to get `WARNING:` and then `BUDGET:` lines (and UI warnings) once the session's estimated spend, coordinator turns plus delegate workers, passes 80% and 100% of that budget. Pi-reported cost is an estimate; the extension cannot see a provider's key or account limit, so set the budget below it. It also cannot detect a coordinator that stalls without an error or a session killed outright: those leave no line.

In the TUI, a compact panel above the prompt shows active workers with their foreground `fg<n>` or background `bg<n>` ID, role, current model and thinking level, elapsed seconds, and latest sanitized tool name. It updates as tools start and once per second, and hides when idle. Ctrl+O expands live delegate tool progress to up to eight recent sanitized tool labels per worker; the collapsed view stays compact. Status never includes task text, tool arguments, or results; the panel also never includes stderr or reasoning.

## Safety and recovery

This is not a sandbox: Pi extensions and `implement`'s Bash run with Pi's operating-system permissions. Read-only workers can read project files; web-enabled ones combine local reads with network access. `guard` asks before matching risky Bash commands (or blocks them when there is no UI), but it is a pattern matcher, not a parser. `implement` worker-side checks block selected commands and disable Git remote protocols, but they do not isolate the process; Git commands in a command that opens with `V=$(mktemp -d …) && cd "$V"` and names no absolute, home, `..`, or other variable path are exempt from the Git rules, so workers can experiment in throwaway repos; some environment or Git options can bypass those checks. Use a clean feature branch, keep the main session out of the checkout until handback, and review the result.

### Limits

Workers have hard time limits of 5 minutes for `scout`, 15 minutes for other read-only roles, and 45 minutes for `implement`; each run has a nominal $5 cost cap. Pi-reported cost is an estimate; it may be absent or overshoot and is not billing authorization. Tool calls are blocked at 80% of the time or cost limit (for `implement`, a 36-minute tool-time window and $4) to prompt a final answer; a worker that ignores three such blocks is terminated on the next blocked call. `scout` alone is capped at 60 tool calls; all other roles have no attempt-count gate and remain subject to the time and cost gates. At most four workers can run at once across calls. Changed limits take effect only after the runtime loads them and do not activate standing A4 recovery. These limits do not make execution safe; per-invocation guard and resource limits remain enforced, and further attempts follow [Standing bounded coordinator recovery — LOAD-GATED](#standing-bounded-coordinator-recovery--load-gated).

### Infra failures

A failed run names its class when the provider's final error explains it: `Failure class: infra` (provider HTTP error such as 409/429/5xx, request timeout, or network failure) or `Failure class: account` (quota, key, or billing limit: a blocker that retrying cannot fix). Other failures, including every limit, cancellation, or crash stop, are model/task failures. The class comes from the error text and says nothing about effects. An `infra` failure is retried automatically on the same model, at most twice (after 15 s, then 60 s), only when its attempt is fully accounted for and ran nothing but replay-safe reads (Pi's own exhausted retry aside), and only while the tool window has time left. Retries run inside the same delegate call and job, share its original deadline and cost caps, and appear as provenance attempts 2–3 and in the details' `Infra retries`. They are not continuations and spend none of the [fixed-slice allowance](#standing-bounded-coordinator-recovery--load-gated). An infra failure after a write, Bash call, or other stop is reported, not retried. Cross-model fallback stays deferred.

### Cancellation, WIP, and tripwires

Cancellation is not rollback. If an `implement` run stops with uncommitted non-ignored changes, the extension may save them in a `WIP(delegate …)` commit on the job branch; a moved branch can prevent that save. Check the handback's branch, commit range, `check` status, and any `Details:` path; inspect the checkout before continuing. A follow-up `implement` recognizes a WIP commit from an earlier attempt and is asked to finish it first.

A `Tripwire` reports that watched shared state changed; it does not restore anything. Stop and inspect the handback and details file before proceeding. Tripwires cover pre-existing Git refs other than the job branch, local Git config other than upstream-tracking entries, files under Git `hooks/` and `info/`, and Pi package, extension, skill, prompt, and theme settings. Treat a failed check, WIP, or tripwire as incomplete work; do not assume the worker rolled back changes. A handback that adds new top-level directories or dot-paths (`.tmp/`, `repro-app/`, `.repro.mts`) lists them with `⚠ new top-level paths`; these are often scratch files, so confirm the task asked for them before accepting.

### Failure provenance

Implement jobs capture bounded, event-derived details for every failed tool call, including targeted tests and non-Bash tools; successful calls and read-only roles are excluded. The private JSON artifact is `<TMPDIR>/me-pi-delegate-<parentPid>/<imN>-failed-tools.json`, linked from the details file and from failed handbacks. Each entry's `disposition` names the cause the parent read from owner facts and the tool result: `budget-blocked`, `guard-denied`, `blocked`, `timeout` (Bash exit 124 or Pi's own command timeout), `nonzero-exit`, `edit-rejected`, `read-failed`, or `unknown`. It is not a worker transcript: effective commands and numeric exit codes appear only when supplied by Pi, and `full_output_path` values are references only—the referenced files are never opened or copied. Explicit-pattern redaction is best-effort (`not guaranteed complete`), so treat the artifact as sensitive and do not share it publicly. If writing it fails, the details and handback show a warning; capture does not change the `check` result or gate, and a successful handback keeps its two-line shape.

Only a properly matched Bash start/end pair whose final result reports `isError: true` and canonical structured `exit_code` from 1 through 127, with no interruption or owner-stop contradiction, is classified `effect: completed`, `replaySafe: false`. The parent-owned `tool-failure/completed` fact and failed-tool artifact remain in history. This is the existing host/tool/hook trust applied symmetrically with a successful Bash result; it records the reported shell termination, not atomicity, containment, or the absence of descendants/external effects. Hook-dropped or contradictory metadata, a signal/high status, denied/limited/unknown outcomes, missing or mismatched call identity, and partial/unclosed calls remain fail-closed. A failed declared check remains failed until a fresh rerun passes; green verification never clears a separate unknown effect. The narrow completed-failure classification permits only same-run repair followed by ordinary finalization; it is not an automatic replay/retry or a change to the current stop-on-block policy.

Pi's JSON `tool_execution_update` event carries a tool-supplied `partialResult`; that is partial output, not a side-effect classification. The delegate records that the runtime reported partial output but does not infer `effect: partial` from it. Pi currently supplies no owner-defined partial-side-effect fact at this boundary, so failed or unfinished calls without a final trusted effect classification remain `unknown` in provenance and may block acceptance. Model/error prose is not effect evidence. Two failures are known to have no effect and add no stop fact: a failed read-only call (`read`, `grep`, `find`, `ls`, `Skill`), and an `edit` that Pi's tool rejected before writing (its own text-mismatch, ambiguity, empty, overlap, no-change, or inaccessible-file errors; `not-started`). A guard or fence denial correlated with its call stays in stop provenance but does not withhold acceptance by itself; whether the denied work was required is the coordinator's judgment.
