# Use and recover delegate workers

The `delegate` tool starts child `pi --mode json -p` workers. A worker sees the task you pass, not the main conversation, so include the relevant paths, context, and acceptance criteria. Ask Pi in ordinary language, for example: “Have a scout trace how this retry path works and return path-and-line evidence.” Read-only workers cannot run shell commands; the coordinating session must supply any needed command output or diff as a file path.

## Roles and tools

- `general` is the default for read-only local investigation. `scout` is a short local lookup with path-and-line evidence. `review` returns severity-ranked findings for the supplied material.
- `research` gathers web sources; `challenge` stress-tests a premise. Both enable web tools by default. They require `pi-web-access`, installed separately (the optional full setup installs the unpinned npm package; to install that extension alone, run `pi install npm:pi-web-access`). Other roles can request web tools with `web: true`; `implement` cannot.
- `implement` is the only role that edits the checkout. Its `edit`/`write` paths are restricted to the real checkout, excluding the Git common directory; it runs the required `check` command and commits there. It requires a clean Git tree on a branch other than `main` or `master`; worker checks block ordinary `gh` and Git push commands. Give it one unchained `check` command; the worker runs it alone, exactly as given, after its final edit. When a skill applies, the coordinator retains its required user decisions and orchestration through completion, including any independent review the skill requires. Workers cannot delegate; a handback completes only the assigned step. Use `background: true` for longer work, then wait for its handback before editing or running Git write commands in that repository.

The package's `Skill` extension adds the `Skill` tool for skills Pi already discovered; it does not supply skills. Filtering the package to `extensions/delegate.ts` does not activate the separate `Skill` extension or the main-session `guard` extension. The delegate implementation still imports sibling helper modules from the package. Install the package, not a copied `delegate.ts` file.

All roles except `implement` are read-only by default. Set `output: true` for a draft: it adds only the `write` tool, restricted to that non-implement worker's fresh private directory under the OS temp directory; the result reports its path. It does not grant `edit`, Bash, or writes to other temporary paths. The main session must review and copy any draft it wants to keep.

## Choose and close work

First honor explicit user-required delegation and any delegation or independent review required by the repo or an applicable skill. Otherwise, delegate bounded, independently checkable work when context savings, parallelism, or independent judgment justify briefing and verification costs; keep coupled decisions with the coordinator. Give each worker a compact, self-contained brief covering scope, deliverable, relevant context and constraints, acceptance evidence, and how to report blockers.

A multi-model panel (`runs`) repeats the same task for each model; decompose work into separate calls with separate briefs. Treat partial answers as incomplete. Explicitly accept, reject, or recover each handback; verify decisive claims proportionately, inspecting implementation diffs and check adequacy without routinely repeating worker work. A final failed or stale declared check, timeout/unknown effect, and WIP commit stay incomplete. An earlier ordinary Bash failure may be repaired within the current worker run; that is not replay or continuation authority, and the final handback still needs a fresh passing check and normal committed delivery. Live UI acceptance requires actual observable evidence from the running interface; static inspection alone does not establish it.

### Coordinator artifacts and verification

The coordinator owns the task ledger and reports outside the checkout. Give workers read-only paths to those artifacts and ask for handbacks, not ledger/report writes; do not relax the implement write fence to accommodate coordinator artifacts. The coordinator records scope, acceptance evidence, the exact declared check, review coverage, and handback/finding dispositions.

Before dispatch, estimate the check/build cost from previous runs or the task's likely verification work and reserve time for verification and a usable handback inside the worker's tool window (36 minutes for the current implement default). There is no universal minute cutoff. Stop starting new behavior when the remaining window is needed for verification and handback. An ordinary failed check does not prohibit repair: within the approved scope and remaining budget, fix the cause and rerun. Any relevant edit after a passing check, including formatter or hook writes, makes the affected evidence stale until rerun; passing results must describe the delivered source.

Choose verification at the strongest supported seam that answers the task, exercising the real owner or event seam rather than a mock mirror, and record what the chosen evidence catches and misses. This evidence-driven default needs no routine user approval of internal test seams and does not load `tdd` or require red-first work. An explicit user or repository test-first/red-first requirement for the task overrides that default: load and follow `tdd` for that requirement.

### One writer and frozen review

Keep one checkout writer, including coordinator writes. Use remaining capacity for independent readers within the existing four-worker limit; do not add concurrent worktree writers or session/clone workarounds. Review a frozen source snapshot: identify its commit or captured diff and baseline, and keep the source stable while reviewers inspect it. The coordinator runs shared checks or Compose only against stable source, never while a writer is changing it. Wait for the existing writer's handback before changing the checkout or starting shared verification.

### Review coverage and closure

Map critical requirements to end-to-end acceptance evidence at the first usable integration point. Request focused independent review when risk warrants it, not after every worker, and do not add a mandatory panel. At final integration, independently review the whole delivered result with separate **Standards** (repository coding standards) and **Spec** (the originating requirements) axes; honor any applicable skill's full review requirements.

The coordinator dispositions routine findings without asking for approval one finding at a time: record required fixes and verify them, reject findings with evidence, or record justified maintenance deferrals that do not waive required acceptance work. Ask when ambiguity changes implementation or a decision requires new authority; required missing work stays incomplete. For a recurring defect class, inspect analogous sites only within the affected owner/scope.

After local fixes, affected-delta closure names the changed source, affected requirements and checks, and the prior Standards/Spec coverage explicitly carried forward. It is not a full-skill review. Reopen broad review for semantic changes, migrations or cross-owner effects, uncertain impact, regressions in previously covered behavior, or an explicit user request. Every invocation of the full review skill still covers both axes. Stop review rounds when current source is fresh-green, required findings are verified, both axes cover delivered behavior, and maintenance judgments have recorded dispositions; do not require endless clean rounds.

After trusted worker termination, effect, checkout, and fixed-slice allowance reconciliation, a qualifying loaded A4 session may handle ordinary repairs/findings and a reconciled worker-limit continuation within the original authority, same selected eligible model, and remaining allowance without a new routine approval. If any standing gate is absent or unverified, proceed only after the user explicitly approves that particular bounded continuation; this task-specific route does not activate standing A4. Both routes preserve the original task/data/provider authority and attempt bases, allow at most two continuations after the initial attempt in that fixed slice, and retain per-attempt limits. Relabeling, splitting, job-ID, or base changes never reset allowance; no attempt may suppress an earlier hook or reuse expired allowance. Reading a plan or newer prose cannot grant a stale runtime authority. A2 provenance is necessary, not sufficient: runtime does not enforce aggregate slice counters or authenticate consent.

## Configure model pools

Optional model pools live at `~/.pi/agent/delegate.json`. Without a file, workers use the main session's model and thinking level; `scout` thinking is capped at `low` (or remains `off`). For model IDs, use IDs available to your Pi installation.

```json
{
  "version": 3,
  "scout": {
    "models": [{ "model": "provider/scout-model", "thinking": "low" }]
  },
  "worker": {
    "models": [{ "model": "provider/worker-model", "thinking": "medium" }]
  },
  "review": {
    "models": [{ "model": "provider/review-model", "thinking": "high" }]
  }
}
```

Replace the example IDs with your provider/model IDs. `review` is optional: when omitted, `review` calls use the `worker` pool; when configured, it is the default pool for `review` only (`general`, `research`, `challenge`, and `implement` keep using `worker`). Pools are role defaults, not allowlists; entry order selects the default model, but it is not a failover sequence. When the model is omitted, only the first candidate is dispatched. **Cross-model fallback is deferred** until Pi supports effective-endpoint enforcement at the fresh child's request boundary and positive scope/budget tests pass. The parent registry snapshot cannot bind the child's effective endpoint; credentials are not read to try to prove otherwise, and model/provider authority is not changed. Current dispatch is first-only; it makes no endpoint or run-scope enforcement claim. Each entry needs a `thinking` value. Scout entries accept `low` or `off`; worker and review entries accept `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`. Optional pool-level `thinking` sets the level for models without a per-model entry; if omitted, the session level is used.

For a one-off choice, the coordinator can set either or both fields in a run, for example `runs: [{ model: "provider/model", thinking: "high" }]`. An omitted model selects the first candidate in the role's pool; an omitted thinking level keeps the configured per-model default, then the pool-level default, then the session level. Any explicitly named model runs alone and never falls back to another model, even if it is listed in the role's pool. An explicit thinking level applies to the selected pool candidate when model is omitted. When a non-review role explicitly names a model that appears in the `review` pool, the role's own pool entry for that model still wins if present; otherwise the documented per-model thinking default applies, and for an unlisted model the role's pool-level default and then the session level apply. Naming a cross-pool model does not inherit review-pool thinking or change role-pool precedence. An unlisted model must be an exact Pi catalog ID in `provider/model` form: Pi's model registry must report it as available with usable authentication. Human-friendly names are not resolved by the tool; the coordinator must provide the exact ID. Scouts remain capped at `low`, or `off` when requested. One-off choices never modify `delegate.json`.

The coordinator continues to own user consent; the delegate does not infer approval from a pool, a typed object, a retry event, or registry metadata. The legacy `fallbackAuthorization` input is scope intent only and does not enable or authorize a destination. A structured `auto_retry_start` event is retained as provenance and yields an explicit cross-model-fallback refusal diagnostic; it does not start another candidate. Quota/billing errors, ordinary unavailable-model messages, and shell-command `429` output are not endpoint evidence or fallback authority. No credentials are read for endpoint checking, and the delegate does not select a different provider on the coordinator's behalf. Existing deadlines, budgets, provenance, and safety stops still apply to the single dispatched candidate.

Pi's JSON `tool_execution_update` event carries a tool-supplied `partialResult`; that is partial output, not a side-effect classification. The delegate records that the runtime reported partial output but does not infer `effect: partial` from it. Pi currently supplies no owner-defined partial-side-effect fact at this boundary, so failed or unfinished calls without a final trusted effect classification remain `unknown` in provenance and may block acceptance. Model/error prose is not effect evidence. These classifications do not enable cross-model fallback; that capability remains deferred pending supported child-boundary enforcement and positive scope/budget tests.

For implement provenance, only a properly matched Bash start/end pair whose final result reports `isError: true` and canonical structured `exit_code` from 1 through 127, with no interruption or owner-stop contradiction, is classified `effect: completed`, `replaySafe: false`. The parent-owned `tool-failure/completed` fact and failed-tool artifact remain in history. This is the existing host/tool/hook trust applied symmetrically with a successful Bash result; it records the reported shell termination, not atomicity, containment, or the absence of descendants/external effects. Hook-dropped or contradictory metadata, a signal/high status, denied/limited/unknown outcomes, missing or mismatched call identity, and partial/unclosed calls remain fail-closed. A failed declared check remains failed until a fresh rerun passes; green verification never clears a separate unknown effect. The narrow completed-failure classification permits only same-run repair followed by ordinary finalization; it is not an automatic replay/retry or a change to the current stop-on-block policy.

Edit the JSON yourself, then `/reload` to reload the extension. Use `/delegate models` to see the config path and `/delegate status` to see pool availability and missing tools.

## Run and stop work

For a long task, ask Pi to use `background: true`. It returns a `bg<n>` job ID; `/delegate status` shows running IDs and recent calls, and `/delegate cancel <id>` requests cancellation. For calls with worker entries, status also shows the stage and active workers' short model name, thinking level, elapsed time, and (for multi-worker calls) worker index; it includes the latest sanitized tool name when available. It never includes task text, tool arguments, or results. At most four workers can run at once across calls. `/reload`, session replacement, or Pi exit ends background jobs; wait for them before reloading when possible. In the TUI, a compact panel above the prompt shows active foreground and background workers with compact foreground `fg<n>` or background `bg<n>` IDs, role, current model and thinking level, elapsed seconds, and latest sanitized tool name. It updates as tools start and once per second for elapsed time, and hides when idle. The panel never includes task text, tool arguments or results, stderr, or reasoning. Ctrl+O still expands live delegate tool progress to show up to eight recent sanitized tool labels per worker; the collapsed view stays compact.

A `research` task needs the separately installed web extension; installing me-pi alone does not provide web tools. Web-enabled workers can read project files as well as fetched pages, so enable web only when outside sources are needed and treat fetched content as untrusted data.

## Safety and recovery

This is not a sandbox: Pi extensions and `implement`'s Bash run with Pi's operating-system permissions. Read-only workers can read project files; web-enabled ones combine local reads with network access. `guard` asks before matching risky Bash commands (or blocks them when there is no UI), but it is a pattern matcher, not a parser. `implement` worker-side checks block selected commands and disable Git remote protocols, but they do not isolate the process; some environment or Git options can bypass those checks. Use a clean feature branch, keep the main session out of the checkout until handback, and review the result.

Workers have hard time limits of 5 minutes for `scout`, 15 minutes for other read-only roles, and 45 minutes for `implement`; each run has a nominal $5 cost cap. Pi-reported cost is an estimate; it may be absent or overshoot and is not billing authorization. Tool calls are blocked at 80% of the time or cost limit (for `implement`, 36 minutes and $4) to prompt a final answer. `scout` alone is capped at 60 tool calls; all other roles have no attempt-count gate and remain subject to the time and cost gates. A worker that ignores three such blocks is terminated on the next blocked call. These limits do not make execution safe. The increased cap takes effect only after the runtime loads this version; it does not activate standing A4 recovery. Per-invocation guard and resource limits remain enforced. Continuation authority and denied-effect handling follow **Current authority boundary** above and **Standing bounded coordinator recovery — LOAD-GATED** below.

Cancellation is not rollback. If an `implement` run stops with uncommitted non-ignored changes, the extension may save them in a `WIP(delegate …)` commit on the job branch. A moved branch can prevent that save. Check the handback's branch, commit range, `check` status, and any `Details:` path; inspect the checkout before continuing. A follow-up `implement` recognizes a WIP commit from an earlier attempt and is asked to finish it first.

Implement jobs also capture bounded, event-derived details for every failed tool call, including targeted tests and non-Bash tools; successful calls and read-only roles are excluded. The private JSON artifact is `<TMPDIR>/me-pi-delegate-<parentPid>/<imN>-failed-tools.json`, linked from the details file and from failed handbacks. It is not a worker transcript: effective commands and numeric exit codes appear only when supplied by Pi, and `full_output_path` values are references only—the referenced files are never opened or copied. Explicit-pattern redaction is best-effort (`not guaranteed complete`), so treat the artifact as sensitive and do not share it publicly. If writing it fails, the details and handback show a warning; capture does not change the `check` result or gate, and a successful handback keeps its two-line shape.

A `Tripwire` reports that watched shared state changed; it does not restore anything. Stop and inspect the handback and details file before proceeding. Tripwires cover pre-existing Git refs other than the job branch, local Git config other than upstream-tracking entries, files under Git `hooks/` and `info/`, and Pi package, extension, skill, prompt, and theme settings. Treat a failed check, WIP, or tripwire as incomplete work; do not assume the worker rolled back changes.

### Standing bounded coordinator recovery — LOAD-GATED

**LOAD-GATED, not unconditionally active.** A coordinator may use one immutable planned slice with one initial attempt and at most two reconciled continuations (three attempts total) only in a session that has loaded the separately approved global policy, supported provenance-capable runtime, and matching reviewed skills, after every activation gate above is satisfied. If any prerequisite is absent or unverified, standing A4 is **INACTIVE** in that session. Reading newer prose cannot grant a stale session authority; the session must be reloaded and revalidated. This is a coordinator/skill contract, not a runtime aggregate gate or consent verifier. Continuations always use the same selected eligible model and original task-data/provider authority. No pool-candidate switch, account/provider evasion, or authority reset is permitted. Keep the slice's original origin/base and every attempt base in the coordinator-owned ledger; relabeling, splitting, changing job IDs, or advancing bases never resets it. Each attempt retains the existing 45-minute hard limit, nominal $5 cap and tool-call limits: at most 135 allocated hard minutes plus possible termination/finalization overhead, not an exact elapsed ceiling or billing guarantee. Runtime does not enforce aggregate slice counters or authenticate consent.

Predeclare and freeze each slice's identity, scope, acceptance evidence, and declared check before its first attempt. Continue only after trusted provenance and reconciliation of worker termination, checkout, and relevant effects. Unknown or partial effects prohibit replay. Preserve scope, acceptance, WIP/history, and the originally authorized data classes, providers/models, and destinations; a continuation grants no new authority. Compare state, usable evidence, and verified findings: useful WIP can count without a fresh green check, while a repeated reason alone does not establish no progress. Halt and record the evidence when allowance is exhausted or no observable progress is shown. When this load gate is satisfied, ordinary stops do not trigger repetitive human prompts. A guard-denied effect remains denied as defined in **Current authority boundary**. Omit optional work only when optionality was predeclared and trusted evidence proves non-execution; required work remains incomplete. Unknown or sensitive integrity effects stop affected writes and acceptance. Never relay a refused mutation through another executor. Any coordinator report uses only pre-existing authority and allowed source evidence. Continue only separable authorized work; accept an unchanged checked commit only while its check evidence remains fresh. Seek a human only for new authority, consequential choices, or unresolved safety. This does not replace the mandatory final integrated independent Standards/Spec review followed by affected-delta closure, and adds no per-job review panel.

**Normative coordinator walkthroughs—not runtime tests or aggregate enforcement:** first-attempt success ends the slice; two continuations exhaust it; relabel/split/job/base changes do not reset it; useful reconciled WIP is progress without green; repeated reason alone is inconclusive; timeout requires termination and state/effect reconciliation; unknown/partial effects block replay; optional denial requires predeclaration plus trusted non-execution while required denial stays incomplete; an unchanged commit is acceptable only with fresh check evidence; human approval is reserved for new authority, consequential decisions, or unresolved safety.
