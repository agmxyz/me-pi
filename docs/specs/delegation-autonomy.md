## Terms and evidence pointers

- **Planned slice:** the predeclared, immutable unit of work authorized for bounded attempts; not a mutable ticket title or worker job ID.
- **Attempt:** one implement worker invocation with its own hard-time and nominal-cost caps. Current dispatch selects only the first configured candidate; cross-model fallback is deferred. An A4 continuation retains the same selected eligible model.
- **Continuation:** a coordinator-initiated later attempt on the same planned slice, after handback and state reconciliation. It is not an automatic runtime retry.
- **Progress:** an observed improvement in state, usable evidence, or a verified finding. A fresh green check is valuable but is not the only progress; unchanged reason text alone does not prove no progress.

## Operating contract

### Verification and ownership

1. At planning, declare the slice scope, acceptance evidence, declared check, and likely check/build cost. Reserve time for that verification inside the 36-minute tool window using actual or estimated check cost; there is no universal minute cutoff.
2. The coordinator owns the task ledger and reports outside the checkout. Workers receive read-only pointers and return handbacks. Do not ask implementers to write coordinator artifacts or relax the write fence.
3. Stop starting new behavior when the remaining window is needed for the check and a usable handback. If a check fails and scope/budget remain, repair the cause and rerun; failure does not ban a fix. Any relevant edit after a passing check makes that evidence stale until rerun.
4. Keep one checkout writer. At most four workers may run; spend remaining slots on independent readers. Review only a frozen source snapshot. The coordinator runs shared checks/Compose only against stable source, not while a writer is changing it.
5. On busy ownership/slots, wait for the existing handback/notification without polling, retry evasion, extra sessions, or queue machinery. Never delete live or unreadable locks. Independent read-only diagnosis or unrelated ready work may proceed.

### Bounded recovery envelope

**Current A4 target, under the 2026-10-30 amendment:** one initial attempt plus at most two reconciled continuations on the same selected eligible model, retaining the original task-data/provider authority. Pool candidate changes and provider/account evasion are outside this target. Cross-model fallback requirements below are preserved as a deferred capability, not current behavior or A4 acceptance.

After the required provenance and policy changes are approved and active:

- The coordinator must enforce each predeclared slice's allowance of **one initial attempt plus at most two continuations**: three attempts total. This is a coordinator-ledger/skill policy obligation, not a runtime-enforced hard gate. Runtime enforcement across jobs would be a separate approved and tested change. Each attempt uses the same 45-minute hard limit and existing per-attempt nominal cost cap; the allocated hard-time budget is at most 135 minutes, not an exact elapsed ceiling. Termination and finalization overhead may add elapsed time. Reported cost may be absent or overshoot; this is not a billing guarantee.
- Preserve scope, resource limits, WIP/history, and acceptance obligations. The coordinator initiates each continuation from a reconciled handback; no hidden runtime retry, automatic resubmission, new supervisor hierarchy, or unattended scheduler.
- The coordinator ledger keeps the planned slice's origin/base and the actual base of each attempt separately. Renaming/relabeling, splitting, changing job ID, or advancing the attempt base never creates a fresh allowance. No alias table or new ledger framework is required.
- **Deferred cross-model capability; original requirement retained:** if later re-authorized, fallback authority must come from a recorded user-approved run contract naming eligible models/providers and permitted task-data classes/destinations, or an explicitly adopted frozen pool snapshot. Configuration alone, issue text, and worker assertions grant no authority. Exact-model instructions override pool eligibility; missing authority prohibits fallback; new candidates or destinations require new authority.
- **Deferred cross-model capability; original budget/effect requirement retained:** any future candidate change must share the original absolute hard/tool deadlines and cumulative hard/tool cost allowances; changing candidates never replenishes them. Before a candidate restart, retain denial/integrity evidence and reconcile checkout and relevant effects. Unknown effects prohibit replay. This deferred behavior is not implemented or part of current A2/A4 acceptance.
- **Current A4 continuation:** retain authority and scope on the same selected eligible model, with each continuation within existing per-attempt caps and the fixed slice envelope. Require termination and trusted effect reconciliation before continuing; a hard timeout may continue only after relevant state/effects reconcile. Unknown effects are never replayed.
- Halt the affected slice when the envelope is exhausted or repeated attempts show no observable state/evidence/finding improvement. Record the comparison; repeating the same reason alone is not a no-progress finding. This reversible trial has no measured optimum. A halt is a reportable disposition, not an automatic request for another human approval.

### Denied effects and authority

**A denied effect remains denied; a local refusal need not suspend the entire run.** Optionality must follow from the predeclared task and acceptance contract, not a worker's assertion after refusal. If that contract leaves optionality ambiguous, the missing work remains incomplete. Under the future approved contract, the coordinator may explicitly abandon an optional forbidden report/cleanup after trusted evidence shows the denied effect did not occur, then continue independently authorized work or accept an unchanged checked commit where its evidence remains fresh. The coordinator may author a report only under pre-existing authority and from allowed source evidence—not as a relay for the refused mutation. A denied optional action needs no new human approval merely to omit it.

Never reproduce a blocked effect through another tool, path, worker, provider, or the coordinator. Required missing work remains incomplete, not success. Unknown or sensitive integrity effects stop affected writes and acceptance; authorized read-only diagnosis and unrelated ready work may continue. Genuine new safety authority, irreversible actions, product/privacy choices, or inability to bound an effect remain human decisions. This spec grants no additional authority beyond an explicit task-specific approval.

|---|---|---|
| Ordinary edit, tool, or test failure | Diagnose and repair within approved scope/budget; rerun affected verification. | Ask only if an implementation-changing choice or new authority is required, or safe progress is impossible. |

### Minimum runtime provenance

The coordinator needs reliable, owner-emitted structured facts; it must not infer policy from model final text, general error regexes, or free-form diagnostics. Keep the contract minimal:

- source/owner and correlated job/attempt/tool-call identity;
- stop/failure cause **separate from resource dimension** (for example, a wrap-up stop due to time versus a hard timeout, cost limit, or scout call cap);
- denied-effect state sufficient to distinguish not-started/denied, completed/partial, and unknown;
- existing delivered-state facts: check `pass`/`stale`/`fail`/`none`, normal commit versus WIP, and integrity/tripwire status.

Retain multiple relevant causes so a time/wrap-up result cannot conceal a guard or integrity signal. Preserve existing checks, snapshots, WIP, commit-range and tripwire guards; add only discriminants/correlation needed to make their ownership usable. Do not create a large event schema, raw-diagnostic log, or telemetry framework. Missing/conflicting provenance fails closed for replay and acceptance, but does not prevent safe read-only diagnosis.

**Deferred cross-model capability requirement, retained from the original plan:** dispatch must receive a small, run-scoped restriction input and enforce eligible candidates, provider, data, and destination scope at the child's effective request boundary. A coordinator record is not authenticated by a typed object. Pi currently exposes no supported boundary enforcement, so current first-only dispatch makes no endpoint/scope enforcement claim. This remains a future capability, not A2's current acceptance.

Provider retry classification must come from its owning structured provider/runtime source. A `429` printed by a failing shell command is not provider evidence. Existing quota/rate-limit text matching may conflate causes; add a failing-command-`429` test before relying on text as provider classification. Unknown provider cause is unavailable/unknown, not transient. Keep existing exact-model behavior and shared attempt budgets. This does not make Pi or worker Bash a malicious-code sandbox.
