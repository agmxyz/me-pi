## User-approved pragmatic verification amendment (current implementation scope)

In addition to the existing safe first-only dispatch scope, accept only a properly correlated Pi Bash completion as `effect: completed`, `replaySafe: false`: canonical structured integer `exit_code` 1–127, `isError: true`, matching completed tool-call start/end identity, and no contradictory interruption or owner facts. Preserve its parent `tool-failure/completed` stop and failed-tool artifact/history; this records reported ordinary command termination under the same trusted host/tool/hook assumption as Bash success. It asserts neither containment, atomicity, descendant/external-effect status, nor replay safety.

Require both `isError: false` and canonical structured `exit_code: 0` before a Bash declared check is a passing baseline. Missing, invalid, conflicting, mismatched, duplicated, unclosed, interrupted, signal/high-status (128+) outcomes; denial, limits, unknown/partial effects, and integrity outcomes remain fail-closed. Fresh green evidence cannot clear a distinct unknown effect. Finalization may ignore a parent `tool-failure/completed` only when exactly one `pi-runtime` Bash effect matches for the same job/attempt/call ID and `replaySafe: false`. This one-to-one rule applies per ordinary completed failure; duplicates, missing facts, any competing stop, or an unsuccessful/stale final check block. This permits repair in the same worker run but grants no auto replay, continuation, or A4 authority.

Tests use Pi's real `createBashTool`, `runToolCall`, and agent-loop interfaces. Cover symmetric successful/nonzero Bash provenance, check freshness, targeted repair and rerun, normal committed delivery, retained failure history, and hook-preserved/dropped/contradictory metadata. Negative cases include high/signal/timeout, mismatched or duplicate correlation, denial/limits, unknown/partial effects, stale changes, WIP and tripwire after green. Runtime trust is symmetric with successful Bash; do not claim coherent hook forgery, descendants, or external effects are authenticated. These are current implementation claims only after the exact check and independent review; A4 remains INACTIVE.

### Endpoint evidence correction (integrated Standards `bg83`)

The installed Pi 1.4.0 runtime does not make `ModelRegistry.find()`'s catalog `baseUrl` the effective request URL in all cases: `ModelRuntime.prepareRequest()` replaces it with `auth.baseUrl` from request-time auth, and GitHub Copilot's OAuth `toAuth()` derives a credential-specific endpoint. `ModelRegistry.getApiKeyAndHeaders()` resolves credentials and is not used for this check; the SDK exposes no credential-free effective-endpoint accessor. The GitLab Duo custom-provider example also changes the request model's base URL inside its stream implementation.

The parent registry snapshot does not bind a fresh child's effective destination: `pi --model` loads its own configuration and resolves request-time authentication after the prompt is supplied. Although some transports use catalog `model.baseUrl`, request-time auth can replace it, OAuth can derive a credential-specific endpoint, and provider extensions can alter the request model's URL. The SDK exposes no supported credential-free accessor or endpoint-only pin at the child request boundary. Therefore the delegate now disables all cross-model fallback, including transports whose catalog metadata appears direct or matching. It does not read credentials to try to establish the endpoint, change model/provider authority, or claim that parent metadata pins the child. The first selected candidate and exact-model behavior remain; shared budgets and provenance still apply to that one dispatched child.

This was a safe fail-closed implementation limitation under the original A2 contract. The 2026-10-30 user-approved amendment now explicitly defers that original functional requirement: current acceptance is trusted provenance and safe first-only dispatch, without endpoint/scope enforcement. Reconsider cross-model fallback only when supported effective-endpoint enforcement exists at the child's request boundary and positive scope/budget regression tests pass.
