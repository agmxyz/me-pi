# Use and recover delegate workers

The `delegate` tool starts child `pi --mode json -p --no-session --no-mcp` workers, each in its own process group with role-specific tools and a deadline. On timeout it stops the worker's process group. A worker sees the task you pass, not the main conversation, so include the relevant paths, context, and acceptance criteria. You don't have to ask for a worker: the coordinator delegates on its own when a task meets the [routing rules](#choose-and-close-work), and you can ask for one explicitly, for example “in the background” or “get a second opinion from another model”. Read-only workers cannot run shell commands; the coordinating session must supply any needed command output or diff as a file path. Installation, package filtering, and the separate `guard` and `Skill` extensions are covered in the [README](../README.md).

## Roles and tools

There are three roles: `general`, `scout`, and `implement`.

- `general` is the default for read-only work of any kind: investigation, review, research, or challenging a plan. The brief defines the work; set `answer` for a specific format (for example severity-ranked `path:line` findings). `scout` is a short, bounded local lookup with path-and-line evidence.
- Web tools are on only when a call sets `web: true`; no role, task wording, or skill name turns them on. They require the separately installed `pi-web-access` extension; me-pi alone provides no web tools (the optional full setup installs the unpinned npm package; to install that extension alone, run `pi install npm:pi-web-access`). `general` and `scout` can take `web: true`; `implement` cannot. Web-enabled workers read project files as well as fetched pages: enable web only when outside sources are needed, and treat fetched content as untrusted data.
- Only `implement` modifies the checkout; `general` and `scout` are read-only by default. `output: true` adds only the `write` tool, restricted to that worker's fresh private directory under the OS temp directory; the result reports its path. It grants no `edit`, Bash, or writes to other temporary paths. The main session must review and copy any draft it wants to keep.
- `implement`'s `edit`/`write` paths are restricted to the real checkout, excluding the Git common directory and a linked worktree's `.git` file. It requires a clean Git tree on a branch other than `main` or `master`; worker checks block ordinary `gh` and Git push commands. Give it one unchained `check` command; the worker runs it alone, exactly as given, after its final edit, and commits there. A worker run of the check inside a pipe, chain, or redirect, or with only extra flags, is blocked, since its result would not be the check's.

Workers load the same `GLOBAL_AGENTS.md` and repo `AGENTS.md` as the main session, minus policy they cannot use: every worker drops `## ` sections whose heading is marked `(coordinator only)`, and read-only workers also drop those marked `(coordinator and implement only)`. Mark a new policy section the same way when it governs only the coordinator or writers.

Workers see neither the main conversation nor the bodies of skills the coordinator loaded: give a self-contained brief, and name any discovered skill the worker should load with `Skill`. Workers cannot delegate; a handback completes only the assigned step. When a skill applies, the coordinator retains its required user decisions and orchestration through completion, including any independent review the skill requires.

## Choose and close work

First honor explicit user-required delegation and any delegation or independent review required by the repo or an applicable skill. Otherwise, delegate only to keep a large read out of the main context or to work in the background: a read over ~3 files, ~300 lines, or ~12 KB, or of unknown scope, goes to `scout`, and web research to `general` with `web: true`; a few reads or a small edit stay inline, even one that needs a review. Keep coupled decisions with the coordinator. Give each worker a compact, self-contained brief covering scope, deliverable, relevant context and constraints, acceptance evidence, and how to report blockers.

A multi-model panel (`runs`) repeats the same task for each model; decompose work into separate calls with separate briefs. Treat partial answers as incomplete. Explicitly accept, reject, or recover each handback. Work from the handback: read only the lines you will act on and spot-check only claims a decision rests on; give a worker any diff or log as a temp file path instead of reading or printing it yourself. An implement ✓ means the extension saw `check` pass on the delivered commit, so do not re-run it. A final failed or stale declared check, timeout/unknown effect, and WIP commit stay incomplete. An earlier ordinary Bash failure may be repaired within the current worker run ([failure provenance](#failure-provenance)); that is not replay or continuation authority, and the final handback still needs a fresh passing check and normal committed delivery. Live UI acceptance requires actual observable evidence from the running interface; static inspection alone does not establish it.

### Coordinator artifacts and verification

The coordinator owns the task ledger and reports outside the checkout, and writes the ledger at the first continuation ([recovery](#bounded-coordinator-recovery)) or when a skill requires it. Give workers read-only paths to those artifacts and ask for handbacks, not ledger/report writes; do not relax the implement write fence to accommodate coordinator artifacts. The coordinator records scope, acceptance evidence, the exact declared check, review coverage, and handback/finding dispositions.

Before dispatch, estimate the check/build cost from previous runs or the task's likely verification work and reserve time for verification and a usable handback inside the worker's wrap-up window ([limits](#limits)). There is no universal minute cutoff. Split work likely to exceed about 1,500 changed lines into frozen slices before its first dispatch, and have workers bound focused test runs with a per-test timeout while iterating. Stop starting new behavior when the remaining window is needed for verification and handback. An ordinary failed check does not prohibit repair: within the approved scope and remaining budget, fix the cause and rerun. Any relevant edit after a passing check, including formatter or hook writes, makes the affected evidence stale until rerun; passing results must describe the delivered source.

Choose verification at the strongest supported seam that answers the task, exercising the real owner or event seam rather than a mock mirror, and record what the chosen evidence catches and misses. This evidence-driven default needs no routine user approval of internal test seams and does not load `tdd` or require red-first work. An explicit user or repository test-first/red-first requirement for the task overrides that default: load and follow `tdd` for that requirement.

### One writer and frozen review

Keep one writer per checkout, including coordinator writes. Use remaining capacity for independent readers within the four-worker limit; do not add a second writer to a checkout, and do not use clones as a workaround. Wait for the active writer's handback before editing, running Git write commands, or starting shared verification in that checkout.

New work is a branch in place by default. When the user asks for a worktree, or accepts the offer made when a checkout is taken, the main session runs `git worktree add ../<repo>.worktrees/<name> -b <branch>`, and the user starts a Pi session there: a session cannot move into another directory. Each worktree has its own `implement` lock, and a job ignores movement of a branch checked out in another worktree, and that branch's `branch.<name>.*` config. `main`, `master`, tags, the stash, other config, and `hooks/` and `info/` stay watched by every job, so do not stash or move `main` while any job runs. While another session's job holds a checkout's lock, this session's `edit`, `write`, and Git tree writes there are blocked; reads and `git worktree add` are not. A git write whose directory is not in the command's text (a `cd` that is not `cd <dir> &&` or `cd <dir>;` opening the command, a shell-expanded path, `--git-dir`, `--work-tree`) is checked against every checkout of the repo, and is blocked while this session's own job runs. When git cannot say whether a job is writing (it times out, or refuses the repository), the call is blocked. The lock (`me-pi-implement.lock` in the checkout's git dir) holds `<session pid> <job id>`, and `<worker pid>` after the first worker spawns; when the session died without releasing it, the checkout stays taken while the worker's process group lives. The refusal names that pid and the lock file: a worker stops at its next tool call; since the pid may have been reused, check it (`ps -o pid,lstart,command -g <pid>`), and if it is not the worker, remove the lock file. Nothing kills it on takeover. A Bash command of that worker runs in its own process group, so it can outlive the worker after the lock reads free. A session started outside the repo is checked only for the paths its commands show. `git worktree remove` or `git worktree move` of a worktree with a running job is blocked in every session, since Git itself removes a clean worktree from under a job; one whose path is not in the command's text is blocked while any linked worktree has a running job. Review a frozen source snapshot: identify its commit or captured diff and baseline, and keep the source stable while reviewers inspect it. The coordinator runs shared checks or Compose only against stable source, never while a writer is changing it.

### Review coverage and closure

Map critical requirements to end-to-end acceptance evidence at the first usable integration point. Do not add a mandatory panel. A review worker is required only when the user, the repo, or an invoked skill asks for one; when the change is over ~50 changed lines (from the handback's `+ins -del` or `git diff --shortstat`); or, at any size, when it touches security or data (secrets, auth or permissions, guard or fence code, destructive or data-migrating code) or breaks a public contract or config format. That review is one `general` worker covering **Standards** (repository coding standards) and **Spec** (the originating requirements), with the diff in a file. Set its `answer` to severity-ranked findings, and send fixes to `implement`, or make small ones inline. Below the gate the coordinator reads the diff itself; that read is the review. Skills that require a full two-axis review keep it.

The coordinator dispositions routine findings without asking for approval one finding at a time: record required fixes and verify them, reject findings with evidence, or record justified maintenance deferrals that do not waive required acceptance work. Ask when ambiguity changes implementation or a decision requires new authority; required missing work stays incomplete. For a recurring defect class, inspect analogous sites only within the affected owner/scope.

After local fixes, affected-delta closure names the changed source, affected requirements and checks, and the prior Standards/Spec coverage explicitly carried forward. It is not a full-skill review. Reopen broad review for semantic changes, migrations or cross-owner effects, uncertain impact, regressions in previously covered behavior, or an explicit user request. Every invocation of the full review skill still covers both axes. Stop review rounds when current source is fresh-green, required findings are verified, both axes cover delivered behavior, and maintenance judgments have recorded dispositions; do not require endless clean rounds.

### Bounded coordinator recovery

A failed handback links this section by absolute path. Recovery is coordinator policy, not runtime enforcement. The coordinator may repair ordinary completed failures (failed test, lint, or typecheck) within the authorized task without asking.

When a worker hits a limit, the coordinator may start a continuation only once the previous worker has stopped, checkout state is known, and every tool effect has a known outcome. At most 2 continuations after the first attempt (3 attempts total), on the same model and provider and within the original scope and authority; renaming, splitting, new job IDs, bases, models, accounts, or providers do not reset the count. A different model or provider needs the user's consent. At the first continuation, not before the first attempt, freeze the slice's identity, scope, acceptance criteria, exact check, original base, and allowance in a coordinator-owned ledger outside the checkout, and record each attempt's base. Every attempt keeps its own caps: three 45-minute attempts allocate at most 135 minutes plus termination overhead.

Stop and report when attempts are exhausted or there is no observable progress (compare state and evidence, not repeated error text). A guard-denied action stays denied: never retry or relay it through another tool, worker, path, session, model, account, or provider. Omit denied optional work only when it was declared optional beforehand and evidence shows it did not run; required work stays incomplete. Unknown or partial effects stop affected writes and acceptance; a passing check does not clear them. Ask the user for new authority, consequential choices (product, privacy, destructive), implementation-changing ambiguity, or unresolved safety, ownership, or effects, not routine completed failures; never reset the allowance yourself. Recovery grants no approval: remote publication, destructive local actions, secret access, configuration changes, personal migrations, installs, reloads, and policy activation stay reserved. Acceptance still requires a fresh passing check on committed work and the review [the gate](#review-coverage-and-closure) requires.

## Configure model pools

Optional model pools live at `~/.pi/agent/delegate.json`. Without a file, workers use the main session's model and thinking level; `scout` thinking is capped at `low` (or remains `off`).

```json
{
  "version": 3,
  "scout": {
    "models": [{ "model": "provider/scout-model", "thinking": "low" }]
  },
  "worker": {
    "models": [{ "model": "provider/worker-model", "thinking": "medium" }]
  }
}
```

Optional top-level `readOnlySkills` lists the skills read-only workers see in their prompt and can load with `Skill`, for example `["code-review", "codebase-design", "diagnosing-bugs", "domain-modeling", "research", "writing-for-agents", "pr"]`; without it they see all discovered skills. Optional top-level `implementSkills` does the same for `implement` workers, for example `["tdd", "diagnosing-bugs", "codebase-design"]`; without it they see all discovered skills. A listed name that Pi did not discover is ignored.

Only `"version": 3` is accepted; an older config (v1 `{ "models": [...], "default": ... }` or v2 string-list pools) fails with an error until it is rewritten in this shape. Replace the example IDs with models available to your Pi installation: a ref may be `provider/id` or, as with Pi's `--model`, a bare model id when exactly one logged-in provider offers it (for example `z-ai/glm-5.3-flash` resolves to `openrouter/z-ai/glm-5.3-flash`); workers get the resolved `provider/id`; an ambiguous ref fails the call, and a ref Pi's catalog does not match passes through unchanged for Pi to resolve. Each entry needs a `thinking` value: scout entries accept `low` or `off`; worker entries accept `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`. Optional pool-level `thinking` sets the level for models without a per-model entry; if omitted, the session level is used. `scout` serves scouts; `worker` serves `general` and `implement`. Pools are role defaults, not allowlists. The first entry is the role's default model, also for concurrent calls; later entries are not a failover sequence. They set the thinking level when a run names that model. The coordinator is not told the pool, so a later entry runs only when you ask for it by name, for example "review this with Sonnet".

The `review` pool was removed: a config that still has a `review` key fails every call with an error pointing here, and the file is never rewritten. To migrate, move the `review.models` entries not already listed into `worker.models` after the first entry, delete `review`, and `/reload`. For a second-opinion review, pass `runs: [{ model: "<review model>" }]`.

For a one-off choice, the coordinator can set either or both fields in a run, for example `runs: [{ model: "provider/model", thinking: "high" }]`; one-off choices never modify `delegate.json`. An omitted model selects the first model in the role's pool, and an explicit thinking level applies to that model. An omitted thinking level keeps the configured per-model default, then the pool-level default, then the session level. Any explicitly named model runs alone and never falls back to another model, even if it is listed in the role's pool. When a role names a model listed only in the other pool, the role's own pool entry for that model still wins if present; otherwise that entry's thinking applies, and for an unlisted model the role's pool-level default and then the session level apply. An unlisted model must resolve the same way to a model Pi's registry reports as available; the tool does no fuzzy matching. Scouts remain capped at `low`, or `off` when requested.

**Cross-model fallback is deferred.** Each run dispatches exactly one model, the one it was given at start, and never switches to another pool entry or provider, whatever the failure; only the same-model infra retry below applies, and a rebuttal round reuses each run's model. Choosing another model after a failure is the coordinator's call, with the user's consent: the delegate infers no approval from a pool, a retry event, or registry metadata. A structured `auto_retry_start` event from Pi is kept as attempt provenance only. Deadlines, budgets, provenance, and safety stops apply to the dispatched run.

Edit the JSON yourself, then `/reload` to reload the extension. `/delegate models` shows the config path; `/delegate status` shows what each pool ref resolves to, whether it is usable, and missing tools.

## Run and stop work

For a long task, ask Pi to use `background: true`. It returns a `bg<n>` job ID; `/delegate status` shows running IDs and recent calls, and `/delegate cancel <id>` requests cancellation. For calls with worker entries, status also shows the stage and each active worker's short model name, thinking level, elapsed time, (for multi-worker calls) worker index, and latest sanitized tool name when available. `/reload`, session replacement, or Pi exit ends background jobs. While any run, `/new`, `/resume`, `/fork`, and `/clone` ask first and stay in the session on a no; Pi has no such hook for `/reload` or exit, so wait for jobs before reloading when possible.

For an external supervisor that watches a file rather than the pane, set `ME_PI_STATUS_LOG=<path>` before starting Pi: when a coordinator turn ends on a provider error after Pi's own retries, the extension appends one `<ISO time> STOPPED: <infra|account|model/task>: <error>` line (account limits add `(BLOCKER: needs the user)`). Set `ME_PI_SPEND_BUDGET_USD=<n>` to get `WARNING:` and then `BUDGET:` lines (and UI warnings) once the session's estimated spend, coordinator turns plus delegate workers, passes 80% and 100% of that budget. Pi-reported cost is an estimate; the extension cannot see a provider's key or account limit, so set the budget below it. It also cannot detect a coordinator that stalls without an error or a session killed outright: those leave no line. Workers do not inherit either variable, so neither they nor their commands write to the log or count against the budget twice.

In the TUI, a compact panel above the prompt shows active workers with their foreground `fg<n>` or background `bg<n>` ID, role, current model and thinking level, elapsed seconds, and latest sanitized tool name. It updates as tools start and once per second, and hides when idle. Ctrl+O expands live delegate tool progress to up to eight recent sanitized tool labels per worker; the collapsed view stays compact. Status never includes task text, tool arguments, or results; the panel also never includes stderr or reasoning.

## Safety and recovery

This is not a sandbox: Pi extensions and `implement`'s Bash run with Pi's operating-system permissions. Read-only workers can read project files; web-enabled ones combine local reads with network access. `guard` asks before matching risky Bash commands (or blocks them when there is no UI), but it is a pattern matcher, not a parser. `implement` worker-side checks block selected commands and disable Git remote protocols, but they do not isolate the process; an implement worker's Git commands in a command that opens with `V=$(mktemp -d [-t name]) && cd "$V"`, and then changes directory only by plain relative paths and names no absolute, home, `..`, or other variable path, are exempt from the Git rules (the main session's guard never exempts them), so workers can experiment in throwaway repos; some environment or Git options can bypass those checks. Use a clean feature branch, keep the main session out of the checkout until handback, and review the result.

### Limits

Workers have hard time limits of 5 minutes for `scout`, 15 minutes for `general`, and 45 minutes for `implement`; each run has a nominal $5 cost cap. Pi-reported cost is an estimate; it may be absent or overshoot and is not billing authorization. Tool calls are blocked at 80% of the time or cost limit (for `implement`, a 36-minute tool-time window and $4) to prompt a final answer; a worker that ignores three such blocks is terminated on the next blocked call. A read-only worker with `output: true` can still `write` into its own output directory after that point, and each such write counts as one of the three. `scout` alone is capped at 60 tool calls; all other roles have no attempt-count gate and remain subject to the time and cost gates. At most four workers can run at once across calls. Workers are asked for answers under ~300 words; a read-only answer over 4 KiB reaches the main session as its head, `[N bytes cut]`, up to three cut `BLOCKED:` lines, and its last 600 bytes, with a path to the full answer. Changed limits take effect only after the runtime loads them. These limits do not make execution safe; per-invocation guard and resource limits remain enforced, and further attempts follow [Bounded coordinator recovery](#bounded-coordinator-recovery).

### Infra failures

A failed run names its class when the provider's final error explains it: `Failure class: infra` (provider HTTP error such as 409/429/5xx, request timeout, or network failure) or `Failure class: account` (quota, key, or billing limit: a blocker that retrying cannot fix). Other failures, including every limit, cancellation, or crash stop, are model/task failures. The class comes from the error text and says nothing about effects. An `infra` failure is retried automatically on the same model, at most twice (after 15 s, then 60 s), only when its attempt is fully accounted for and ran nothing but replay-safe reads (Pi's own exhausted retry aside), and only while the tool window has time left. Retries run inside the same delegate call and job, share its original deadline and cost caps, and appear as provenance attempts 2–3 and in the details' `Infra retries`. They are not continuations and spend none of the continuation allowance. An infra failure after a write, Bash call, or other stop is reported, not retried. Cross-model fallback stays deferred.

### Cancellation, WIP, and tripwires

Cancellation is not rollback. If an `implement` run stops with uncommitted non-ignored changes, the extension may save them in a `WIP(delegate …)` commit on the job branch; a moved branch can prevent that save. Check the handback's branch, commit range, `check` status, and any `Details:` path; inspect the checkout before continuing. A follow-up `implement` recognizes a WIP commit from an earlier attempt and is asked to finish it first.

A `Tripwire` reports that watched shared state changed; it does not restore anything. Stop and inspect the handback and details file before proceeding. Tripwires cover pre-existing Git refs other than the job branch, local Git config other than upstream-tracking entries, files under Git `hooks/` and `info/`, and Pi package, extension, skill, prompt, and theme settings. Treat a failed check, WIP, or tripwire as incomplete work; do not assume the worker rolled back changes. A handback that adds new top-level directories or dot-paths (`.tmp/`, `repro-app/`, `.repro.mts`) lists them with `⚠ new top-level paths`; these are often scratch files, so confirm the task asked for them before accepting.

### Failure provenance

Implement jobs capture bounded, event-derived details for every failed tool call, including targeted tests and non-Bash tools; successful calls and read-only roles are excluded. The private JSON artifact is `<TMPDIR>/me-pi-delegate-<parentPid>/<imN>-failed-tools.json`, linked from the details file and from failed handbacks. Each entry's `disposition` names the cause the parent read from owner facts and the tool result: `budget-blocked`, `guard-denied`, `blocked`, `timeout` (Bash exit 124 or Pi's own command timeout), `nonzero-exit`, `edit-rejected`, `read-failed`, or `unknown`. It is not a worker transcript: effective commands and numeric exit codes appear only when supplied by Pi, and `full_output_path` values are references only—the referenced files are never opened or copied. Explicit-pattern redaction is best-effort (`not guaranteed complete`), so treat the artifact as sensitive and do not share it publicly. If writing it fails, the details and handback show a warning; capture does not change the `check` result or gate, and a successful handback keeps its two-line shape.

Only a properly matched Bash start/end pair whose final result reports `isError: true` and canonical structured `exit_code` from 1 through 127, with no interruption or owner-stop contradiction, is classified `effect: completed`, `replaySafe: false`. The parent-owned `tool-failure/completed` fact and failed-tool artifact remain in history. This is the existing host/tool/hook trust applied symmetrically with a successful Bash result; it records the reported shell termination, not atomicity, containment, or the absence of descendants/external effects. Hook-dropped or contradictory metadata, a signal/high status, denied/limited/unknown outcomes, missing or mismatched call identity, and partial/unclosed calls remain fail-closed. A failed declared check remains failed until a fresh rerun passes; green verification never clears a separate unknown effect. The narrow completed-failure classification permits only same-run repair followed by ordinary finalization; it is not an automatic replay/retry or a change to the current stop-on-block policy.

Pi's JSON `tool_execution_update` event carries a tool-supplied `partialResult`; that is partial output, not a side-effect classification. The delegate records that the runtime reported partial output but does not infer `effect: partial` from it. Pi currently supplies no owner-defined partial-side-effect fact at this boundary, so failed or unfinished calls without a final trusted effect classification remain `unknown` in provenance and may block acceptance. Model/error prose is not effect evidence. Two failures are known to have no effect and add no stop fact: a failed read-only call (`read`, `grep`, `find`, `ls`, `Skill`), and an `edit` that Pi's tool rejected before writing (its own text-mismatch, ambiguity, empty, overlap, no-change, or inaccessible-file errors; `not-started`). A guard or fence denial correlated with its call stays in stop provenance but does not withhold acceptance by itself; whether the denied work was required is the coordinator's judgment.
